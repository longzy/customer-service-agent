## 1. 客户新闻稿（Press Release）

### 标题
客户和坐席，看到同一套新界面

### 副标题
客户在等待人工时看得懂进度，坐席在队列里扫得快、领得准。

### 摘要
现有两个前端停留在原型样式：客户侧聊天页没有品牌与等待反馈，坐席侧是单列卡片队列，没有列宽、超时与状态区分。本切片按已冻结的设计稿重做客户侧与坐席侧页面，统一令牌与组件契约，等待与队列状态第一次“看得见”。

### 问题
客户不知道自己在排第几、还要多久；坐席在一堆卡片里找不到最久的会话，也不知道哪些已经超时。界面不像一个可交付的产品，视觉与交互都无法支撑 M1 的岗位走查。

### 方案
客户登录后看到品牌化的对话页，转人工时有明确的等待卡（状态说明、可继续补充）；坐席登录后看到标准后台三栏：左侧导航、中间可筛选排序的队列表格、右侧会话详情。超时、状态、权限与键盘流都有明确表达。

### 引语（Quote）
> “待补（需真实走查）”
> —— 客户/坐席，2026-11-18

### 行动号召
无需新增入口。客户继续用 `/login` 与 `/chat`，坐席继续用 `/login` 与 `/queue`；上线后同一套账号与流程，只换界面。

## 2. 常见问题（FAQ）

### 2.1 外部 FAQ（客户/用户会问）

| 问题 | 回答 |
|---|---|
| 谁会用到？ | 客户甲/乙与坐席 1/2；不新增角色。 |
| 怎么用？ | 客户登录→聊天→转人工→看等待；坐席登录→队列→筛选→领取→接管。流程不变。 |
| 数据/隐私怎么处理？ | 不新增数据字段；详情面板继续只展示脱敏后的最近消息，并带“已脱敏”提示。 |
| 失败/不可用时怎么办？ | 队列加载失败可重试；无权限与空队列明确区分；领取冲突提示并刷新。 |

### 2.2 内部 FAQ（评审者会问）

| 问题 | 回答 |
|---|---|
| 为什么现在做？ | 设计稿与令牌已冻结；旧样式无法支撑 M1 岗位走查；后续切片会继续在旧样式上叠加，越晚改越贵。 |
| 成功度量是什么？ | AC-40~AC-49 全绿；两应用与基线截图比对无“需修/阻断”；`verify` 前端步骤通过。 |
| 不做会怎样？ | 客户侧缺少等待反馈，坐席侧缺少超时与键盘流；后续订单/取消切片继续背旧样式。 |
| 范围与非目标是什么？ | 范围内：令牌接入、客户登录/聊天、坐席登录/队列/详情/四态/键盘流、响应式与基线比对。非目标：后端、API、权限、状态机、移动端新设计、暗色模式、i18n、共享组件包。 |
| 依赖与假设是什么？ | 现有接口与 `lib/api-types.ts` 不变；两个应用各自维护组件（已批准决策）；CSS Modules 可用；`tokens.css` 能通过相对路径被 Next 构建读取。 |
| 主要风险与缓解是什么？ | Next 跨目录 `@import` 可能被拒（S1 先验证，失败则用同步脚本+一致性检查）；ChatShell 334 行需拆分；现有前端测试按旧结构查询会失效（同步更新断言）；视觉回归靠基线人工比对。 |
| 备选方案是什么？ | 一次改完两应用（否决：评审与回滚不可控）；建共享组件包（否决：已批准两应用各自维护）；继续全局类名（否决：与 2.6 CSS Modules 冲突）。 |
| 成本、周期、上线与回滚？ | 3 个切片 S1/S2/S3，约 3–4 天；一次发布、三次提交；S2/S3 可独立回滚，S1 为机械改动。 |
