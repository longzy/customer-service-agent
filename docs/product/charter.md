# 产品宪章

> 2026-11-16 方向重置：目标改为“企业内部 AI 客服系统”。本文的 M1 消费者定位已归档为 M1-P 原型；新基线见 [企业化方向重置](../initiatives/2026-11-16-enterprise-reset.md)。R0-1 完成前，不以本文旧用户/里程碑作为新开发依据。


## 1. 项目使命

建设一套以电商客服为业务场景的企业级 Customer Service Agent，重点证明 Agent 不仅能回答政策问题，还能在明确权限和业务约束下，安全、可追踪地完成业务任务。

## 2. 目标用户

### M1 直接用户

需要查询订单或取消未发货订单的消费者。

### 后续用户

- 需要接管复杂问题和审批高风险操作的人工客服。
- 需要配置知识、规则、权限和评估集的运营人员。
- 需要观察任务成功率、失败节点和成本的平台管理员。

## 3. 要解决的问题

- 用户无法快速定位订单与适用的售后政策。
- 传统 Chatbot 能解释规则，却不能可靠地完成业务操作。
- 多系统调用存在重复提交、越权、超时和执行结果不明确的风险。
- Agent 失败后，人工接管缺少上下文，难以定位问题。
- 模型、Prompt 或工具升级后，无法证明任务成功率没有退化。

## 4. 产品原则

- 任务完成优先于回答流畅。
- 确定性业务规则优先于模型自由判断。
- 服务端授权优先于 Prompt 约束。
- 可恢复和可审计优先于一次性调用成功。
- 评测证据优先于主观演示。
- 全局架构稳定，当前规格按里程碑演进。

## 5. 首个业务闭环

M1 只覆盖：

```text
用户查询本人订单
  -> Agent 识别订单和取消意图
  -> 服务端校验身份、租户和订单归属
  -> 确定性规则判断是否允许取消
  -> 向用户说明结果并获取确认
  -> Workflow 幂等提交取消
  -> 查询并确认业务系统结果
  -> 向用户反馈或转人工
```

### M1 范围

- Web Chat 单渠道。
- 查询当前用户有权访问的订单。
- 未发货且符合规则的订单取消。
- 不符合条件时解释原因，不提交操作。
- 多订单歧义时先澄清。
- 重复提交、接口超时、未知结果和人工接管。
- 每次执行具有 Trace 和审计事件。

### M1 非目标

- 真实支付、退款到账和财务对账。
- 已发货订单拦截、改址和物流拦截。
- 商品推荐、营销和优惠券计算。
- 多渠道适配、语音和电话。
- 完整客服工作台与质检系统。
- 多 Agent 自主协商。
- 生产级多租户计费和运营分析。

## 6. 成功指标

M1 的首要指标是：

> 在封存的业务评测集上，经业务系统核验的任务成功率。

辅助指标：

- 未授权查询和操作拦截率必须为 100%。
- 相同幂等请求造成的重复取消申请数必须为 0。
- 写接口超时后的可恢复率。
- 不符合条件时被错误提交的操作数必须为 0。
- 人工接管时上下文、工具轨迹和待处理步骤的完整率。
- 模型、Prompt 和 Tool 版本之间的回归通过率。

## 7. 关键假设

- M1 使用可控的模拟 OMS，不依赖真实企业接口。
- 首版消费者只能操作本人、同一租户内的订单。
- 订单是否可取消由服务端规则决定，不由模型决定。
- 高风险操作需要用户明确确认；后续可加入人工审批阈值。

## 8. 产品待决事项

- 人工审批触发阈值。
- 退款是否作为 M2 的第一优先场景。
- 首个 Web Chat 是否需要坐席工作台的最小视图。
- 模型成本和延迟目标。
