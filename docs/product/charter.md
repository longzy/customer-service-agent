## 1. 项目使命

建设一套**企业内部 AI 客服系统**：AI 默认自动回复客户并完成订单类任务，客户可随时转人工，人工坐席在工作台接管并闭环。

系统交付的是可运营的客服能力，不是消费者聊天 demo，也不是通用问答机器人。判断标准是客户与坐席两条岗位路径能否真实走通，而不是接口或 AC 的数量。

## 2. 目标用户与角色

| 角色 | 是谁 | M1 职责 | 入口 |
|---|---|---|---|
| 客户 | 企业外部消费者，匿名 | 发消息、查单、取消、要求人工、接收回复 | 客户 Web Chat |
| AI 助手 | 系统能力 | 自动回复；按意图调用订单 Tool；低置信、客户要求或高风险时转人工 | 客户 Web Chat |
| 坐席（`agent`） | 企业内部客服人员 | 登录、领取会话、查看上下文、接管、回复、取消、关闭或转回 AI | 坐席工作台 |
| 主管（`supervisor`） | 客服团队管理者 | 团队队列、分配、审计（M4） | 坐席工作台 |
| 管理员（`admin`） | 系统管理员 | 员工账号、角色、集成配置（M4） | 坐席工作台 |

M1 的员工角色**只有 `agent`**（2026-11-16 确认）。RBAC 在服务端校验，权限模型保留角色维度，但不建设账号管理界面；`supervisor`/`admin` 的权限与界面到 M4 实现。员工账号由迁移或种子脚本创建。

## 3. 要解决的问题

- 客户等待时间长，重复描述问题，转人工后仍要从头说明。
- AI 失败或越界后没有队列、坐席和接管，转人工成为死路。
- 业务操作缺少服务端授权、幂等和审计，无法证明“谁在什么权限下做了什么”。
- 模型、Prompt 或 Tool 升级后，无法证明自动回复与任务成功率没有退化。
- 演示级身份、会话和队列无法支撑企业内部真实运营。

## 4. 产品原则

- 真实业务闭环优先于演示效果；主路径不允许 Mock。
- 岗位端到端优先于 AC 数量；评审按客户和坐席两条路径走查。
- 服务端授权优先于 Prompt 约束或前端隐藏。
- 确定性业务规则优先于模型自由判断。
- 可恢复、可审计优先于一次性调用成功。
- Mock 只允许存在于适配器和测试，且只针对外部业务系统。
- 模块边界先于功能：先立边界，再在边界内加能力。

## 5. M1 核心闭环

```text
客户匿名进入 Web Chat（可选昵称）
  -> 发送消息
  -> AI 自动回复；查单/取消时调用受控 Tool
  -> 客户要求人工 / AI 低置信 / 高风险 / 规则要求
  -> 生成交接单（摘要 + 订单 + AI 轨迹 + 待办）进入队列
  -> 坐席登录工作台，领取会话
  -> 查看客户、消息、订单、AI 轨迹
  -> 接管，客户看到“人工已接入”
  -> 回复；符合条件的取消经确认后由 Workflow 提交
  -> 关闭会话或转回 AI
```

订单访问采用**订单号 + 下单手机号后四位**校验：客户在会话内首次查单或取消前提供，服务端向 OMS 校验；校验结果只在当前会话内复用，新会话重新校验。校验失败不区分“订单不存在”与“手机号不匹配”，并做限速。

## 6. M1 范围

### 包含

- 客户匿名 Web Chat 单渠道；可选昵称；同一浏览器会话可恢复。
- 员工本地账号、服务端 session、服务端 RBAC（M1 仅 `agent` 角色）。
- AI 自动回复；订单查询与取消 Tool；确定性转人工规则。
- 交接单、队列、坐席领取、接管、回复、关闭、转回 AI。
- 坐席工作台独立前端：会话列表、消息、客户与订单信息、AI 轨迹、交接单。
- 审计、Trace、outbox/worker 与持久化。
- 场景评测覆盖核心路径；客户与坐席两条岗位路径端到端走查。
- 单企业单租户部署；数据模型保留租户维度，不建设租户管理界面。

### 不包含

- 客户账号、客户登录与客户身份体系（M4+）。
- 主管/管理员角色与界面、账号管理、排班、质检、运营后台（M4）。
- OIDC/SSO/MFA/SCIM（M5）。
- 真实 OMS、支付、物流；退款与审批（M2）。
- 知识库/RAG、FAQ 运营、商品导购（M3）。
- 全渠道、语音、电话。
- 多 Agent 自主协商；微服务、Kafka、K8s。

## 7. Mock 边界

| 允许 Mock | 不允许 Mock |
|---|---|
| OMS 的订单查询、取消资格、提交取消、结果查询 | 员工身份、密码、session、RBAC |
| 支付/物流（M2 及以后） | 客户会话、消息、交接单、队列、分配、接管、回复、关闭 |
| 测试中的模型与外部服务 | 坐席工作台、审计、Trace、持久化 |

规则：

- Mock 只允许出现在 `services/adapters/` 与测试中。
- 业务模块不得 import `mock_oms` 或任何具体 Adapter，只能依赖 `OmsPort`。
- 生产环境缺少 OMS 配置时必须启动失败，不得静默回落到 Mock。

## 8. 成功指标

首要指标：

> 客户与坐席两条岗位路径端到端走通，并以封存评测集和业务系统核验为证据。

辅助指标：

- 越权拦截率 100%：未登录不能进工作台；坐席只能操作可领取或本人已接管的会话；客户不能读取他人会话。
- 死路 handoff 数为 0：每次转人工都能进入队列并被领取或关闭。
- 相同幂等请求造成的重复取消数为 0；规则不符时误提交数为 0。
- 接管时上下文完整率 100%：消息、订单、AI 轨迹、待办。
- 模型、Prompt 与 Tool 版本之间的回归通过率。
- 封存评测集上的自动回复任务成功率。

## 9. 关键假设与约束

- 客户在 M1 保持匿名，不建账号（2026-11-16 确认）。
- 订单访问以订单号 + 手机尾号为准，M1 不接短信（2026-11-16 确认）。
- 只有 OMS（以及 M2 后的支付/物流）允许 Mock；身份、会话、队列、工作台、审计必须真实。
- 取消资格、用户确认与幂等由服务端确定性代码决定，不由模型决定。
- 员工使用本地认证；OIDC/SSO 后置到 M5。
- 客户聊天与坐席工作台是两个前端、两个入口，不共用页面。
- M1 单企业单租户部署，保留租户维度以兼容后续隔离。
- M1 队列领取优先，不做自动分配（D-011）。
- M1 保留：会话 24h、消息/交接单 30d、审计 90d；不保存完整手机号（D-012）。
