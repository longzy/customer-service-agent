这份电商智能客服系统的设计，整体方向是正确的，而且覆盖了当前企业级 Agent 客服系统的主要业务能力。

但如果从企业级产品设计、Agent 工程架构、实际落地可行性三个角度评审，我的判断是：



整体方向合理

架构设计尚不完整



它目前更像一份完整的产品功能清单，而不是一份可以直接指导研发的系统设计方案。

它回答了系统应该具备哪些功能，但还没有充分回答几个更关键的问题：

1. Agent 如何理解用户需求，并决定下一步做什么？
2. Agent 如何安全地执行订单、退款、改址等业务操作？
3. 多个 Agent 如何协作，如何控制执行流程？
4. 如何保证业务操作不重复、不越权、不产生错误结果？
5. 如何测试 Agent 的可靠性，如何定位执行失败的原因？

尤其是后面三个问题，才是企业级 Agent 系统真正的工程难点。

下面具体分析。

# 一、现有六大模块的设计评审

| 模块         | 评价     | 主要问题                    |
| ---------- | ------ | ----------------------- |
| 全渠道接入与会话管理 | 合理     | 缺少统一会话模型、渠道适配层设计        |
| 售前智能导购     | 合理     | 推荐策略、商品检索、促销规则边界不清楚     |
| 售后自动化闭环    | 非常重要   | 缺少业务状态机、操作授权和异常补偿       |
| AI 大脑      | 需要重点调整 | 多 Agent 设计偏概念化，缺少执行编排机制 |
| 人工坐席辅助与质检  | 合理     | 缺少人机协作和人工接管机制           |
| 数据与运营能力    | 合理     | 缺少数据追踪、评估体系和成本管理        |

## 1. 全渠道接入与会话管理

这部分属于传统客服系统的基础设施，整体设计没有明显问题。

但有一个重要的架构问题：

不同渠道不应该直接进入 Agent，而应该先经过统一的接入层和会话层。

例如：

- 微信消息：微信适配器
- 淘宝消息：淘宝适配器
- Web 消息：WebSocket 接入
- 电话：语音识别与转写

这些渠道需要统一转换成内部消息格式。

建议增加：

- Channel Adapter：渠道适配器
- Conversation Manager：会话管理
- User Identity Resolver：用户身份关联
- Session Context：会话上下文
- Human Handoff：人工接管

另外，Redis 保存 72 小时上下文只是一个实现示例，并不是完整的记忆方案。

应该区分：

| 数据类型   | 存储方式              |
| ------ | ----------------- |
| 实时会话状态 | Redis             |
| 历史对话记录 | PostgreSQL / 消息存储 |
| 用户画像   | CRM / 用户中心        |
| 长期业务记忆 | 结构化业务数据           |
| 知识库    | 向量数据库 + 原始文档存储    |

不要把用户的全部历史对话都当成 Agent Memory。

## 2. 售前智能导购

这是一个相对独立的业务域。

其中需要区分三个能力：

- 商品知识查询：商品有什么属性、适合什么场景。
- 商品实时查询：当前库存、价格、SKU 是否可售。
- 商品推荐决策：根据用户需求筛选和推荐商品。

这三种能力背后的技术实现并不相同。

例如：

用户问：

> 想给妈妈买一个 1000 元左右的按摩仪，主要用于缓解肩颈疲劳。

Agent 需要：

1. 提取预算、商品类型、使用场景。
2. 检索商品目录。
3. 查询实时库存和价格。
4. 根据商品属性进行筛选。
5. 生成推荐理由。
6. 根据用户反馈继续缩小范围。

这里有一个值得注意的问题：

商品知识不能完全依赖 RAG。

商品价格、库存、优惠券等具有实时性和强一致性要求的数据，应通过业务 API 查询，而不是依赖向量数据库中的历史文档。

## 3. 售后自动化闭环

整个系统最值得深入设计的模块

我认为这部分是电商 Agent 最能体现实际业务价值的地方。

但原方案有一个比较大的缺失：

把业务 API 调用等同于业务执行完成。

实际上，退款、改址、取消订单等操作都有严格的业务约束。

例如退款：

```
用户申请退款
    ↓
识别订单
    ↓
验证用户身份
    ↓
查询订单状态
    ↓
判断是否允许退款
    ↓
计算可退款金额
    ↓
获取用户确认
    ↓
提交退款申请
    ↓
等待业务系统处理
    ↓
查询退款结果
    ↓
通知用户
```

注意，这里面至少存在三种不同的结果：

- Agent 已经发起退款。
- 退款系统已经受理。
- 退款已经实际到账。

不能把它们统一理解为退款成功。

建议引入以下工程机制：

| 机制                       | 解决的问题             |
| ------------------------ | ----------------- |
| Workflow / State Machine | 控制业务执行步骤          |
| Policy Engine            | 校验退款、改址等业务规则      |
| Permission Guard         | 控制用户和 Agent 的操作权限 |
| Idempotency              | 防止重复退款、重复提交       |
| Human Approval           | 高风险操作人工确认         |
| Compensation             | 处理业务执行失败和部分成功     |
| Audit Log                | 记录操作人、执行过程和结果     |

这部分如果设计得好，才是真正的企业级 Agent 工程。

## 4. AI 大脑：意图识别 + RAG + 多 Agent

这一部分是我认为原方案最需要重新设计的地方。

原方案采用：

- 主控 Agent
- 商品 Agent
- 订单 Agent
- 物流 Agent
- 售后 Agent
- 营销 Agent

这种划分在产品介绍中很直观，但不意味着实际系统就应该采用六个独立 Agent。

### 问题一：为什么一定要使用多 Agent？

例如用户说：

> 我的订单还没发货，能不能帮我取消？

这个请求实际上涉及：

1. 订单查询
2. 订单状态判断
3. 取消规则校验
4. 取消操作
5. 结果确认

这些步骤完全可以由一个主 Agent 配合订单工具和业务 Workflow 完成。

如果把每个业务能力都拆成独立 Agent，反而会增加：

- Agent 间通信成本
- 上下文传递成本
- 执行路径复杂度
- 错误定位难度
- Token 消耗

我更建议采用：

一个主 Agent + 多个领域工具 + 必要的业务子 Agent + Workflow。

例如：

Customer Service Agent

理解需求、意图判断、任务规划、工具选择

Knowledge Tools

商品知识 / FAQ / 售后规则

Business Tools

订单 / 库存 / 物流 / 退款

Recommendation

商品筛选 / 个性化推荐

After-sales Workflow

退款 / 退换货 / 工单

Execution Guardrails

权限、参数校验、风险控制、人工审批、执行审计

External Business Systems

OMS / ERP / CRM / WMS / 支付 / 物流

这里的重点是：领域能力不一定等于领域 Agent。

商品查询可以是 Tool，退款可以是一个有状态的 Workflow，只有确实需要独立推理、独立上下文或复杂任务规划时，才考虑拆分子 Agent。

### 问题二：RAG 的职责边界不够清晰

建议将知识分成三类：

| 类型   | 示例         | 实现方式           |
| ---- | ---------- | -------------- |
| 静态知识 | 商品说明书、FAQ  | RAG            |
| 业务规则 | 退换货条件、优惠规则 | 结构化规则引擎 + 知识检索 |
| 实时数据 | 订单、库存、价格   | API / 数据库查询    |

尤其是售后规则，不能只依赖向量检索召回结果做最终判断。

RAG 负责提供知识依据，规则引擎负责确定业务是否允许执行。

### 问题三：缺少 Agent 执行编排机制

原方案提到了 Tool Calling，但没有说明：

- 工具如何注册和发现？
- 如何决定工具调用顺序？
- 如何处理工具超时？
- 如何重试？
- 如何处理工具调用失败？
- 如何恢复中断的任务？
- 如何限制 Agent 无限循环调用工具？
- 如何保存每次执行的中间状态？

这些都是 Agent Runtime / Harness Engineering 应该解决的问题。

我建议将 AI 大脑拆成几个明确的工程层次：

| 层次              | 核心职责            |
| --------------- | --------------- |
| Intent Router   | 识别用户意图及任务类型     |
| Agent Runtime   | 管理模型调用、上下文和工具执行 |
| Tool Registry   | 工具注册、描述、权限和版本   |
| Workflow Engine | 管理多步骤业务流程       |
| Policy Engine   | 业务规则和风险控制       |
| Execution Guard | 参数验证、调用限制、结果校验  |
| State Manager   | 执行状态持久化和恢复      |

这样才有比较清晰的研发边界。

## 5. 人工坐席辅助与质检

这部分设计比较完整，但我认为还缺少一个重要概念：

Human-in-the-loop（人机协同）。

人工坐席不应该只是 Agent 失败后的兜底渠道。

建议设计三种工作模式：

| 模式     | 执行方式           | 典型场景      |
| ------ | -------------- | --------- |
| AI 全自动 | Agent 独立处理     | 查物流、查订单   |
| AI 辅助  | AI 提供建议，人工确认   | 商品推荐、复杂咨询 |
| 人工审批   | AI 准备操作，人工授权执行 | 大额退款、特殊补偿 |

另外，人工接管需要保留：

- 完整对话上下文
- 已经调用的工具
- 已查询到的业务数据
- 当前 Workflow 状态
- 失败原因和待处理步骤

否则人工客服接管之后，还要重新询问用户，系统体验会很差。

## 6. 数据与运营能力

这一模块还需要补充一个重要方向：Agent 运行质量评估。

传统客服指标主要关注：

- 首次响应时间
- 客户满意度
- 人工转接率
- 问题解决率

但 Agent 系统还需要关注：

| 指标                          | 衡量内容      |
| --------------------------- | --------- |
| Intent Accuracy             | 意图识别准确率   |
| Tool Selection Accuracy     | 工具选择准确率   |
| Tool Execution Success Rate | 工具执行成功率   |
| Task Completion Rate        | 任务完成率     |
| Groundedness                | 回答是否有可靠依据 |
| Policy Violation Rate       | 是否违反业务规则  |
| Human Handoff Rate          | 人工接管比例    |
| Cost per Resolution         | 单次问题解决成本  |

特别要区分：

回答正确率 ≠ 业务任务完成率。

例如，用户要求退款，Agent 正确解释了退款政策，但没有真正完成退款申请，这不应该被统计为任务成功。

建议建设独立的 Agent Evaluation 模块，支持：

1. 测试数据集管理。
2. 对话场景模拟。
3. Tool Calling 轨迹记录。
4. Agent 执行过程评估。
5. 模型、Prompt、Tool 版本对比。
6. 失败节点分析。
7. 业务任务成功率统计。

这对于企业持续升级 Agent 非常重要。

# 二、原方案还缺少哪些企业级基础设施？

如果把这套系统作为一个真正的企业产品，我认为至少还需要补充以下五个方面。

| 能力         | 具体设计                           | 重要性 |
| ---------- | ------------------------------ | --- |
| 多租户与数据隔离   | 品牌、店铺、用户、知识库隔离                 | 必须  |
| 安全与权限      | 身份认证、数据权限、工具授权、敏感信息脱敏          | 必须  |
| Agent 可观测性 | Trace、Log、Token、Tool Call、执行链路 | 必须  |
| 可靠性保障      | 超时、重试、幂等、熔断、任务恢复               | 必须  |
| Agent 评估   | Benchmark、离线评估、线上评估、回归测试       | 必须  |

其中，我特别强调三个容易被忽略的问题。

1\. 数据权限隔离

假设一个客服同时管理三个店铺，Agent 不能因为用户提供了另一个订单号，就查询到其他店铺的数据。

不能仅依靠 Prompt 告诉模型不要越权，必须在业务 API 和 Tool 执行层进行权限校验。

2\. 执行链路可观测性

需要能够还原一条完整链路：

```
用户消息
  └── Intent Classification
       └── Agent Planning
            └── Tool Call
                 └── API Request
                      └── API Response
                           └── Result Validation
                                └── Final Response
```

发生问题时，能够定位到底是意图识别错误、工具选择错误、参数错误、业务 API 失败，还是模型错误地理解了执行结果。

3\. 业务操作安全

退款、改址、取消订单等操作，不能完全交给 LLM 自由决定。

应该采用确定性的业务规则和权限控制，将 LLM 的决策能力限制在允许的操作范围内。

# 三、如果真正要研发，建议重新划分系统架构

我建议不要再按照六大业务模块组织整个技术架构，而是按照企业 Agent 系统的职责边界划分。

可以分成七层：

L1. Channel Layer｜渠道接入层

Web、APP、微信、抖音、电话、人工坐席

L2. Customer Service Core｜客服业务核心层

会话管理、用户身份、客户画像、工单、人工接管

L3. Agent Orchestration｜Agent 编排层

意图路由、任务规划、Agent Runtime、Workflow、上下文管理

L4. Agent Capability｜Agent 能力层

商品问答、智能导购、订单查询、物流、售后、营销

L5. Tool & Integration｜工具与集成层

Tool Registry、API Adapter、RAG、CRM、OMS、ERP、WMS

L6. Governance & Security｜治理与安全层

权限、策略、风险控制、审计、人工审批、执行保护

L7. Observability & Evaluation｜可观测与评估层

Tracing、Logging、Metrics、Benchmark、质量评估、成本分析

这里有一个架构上的注意点：第六层和第七层并不是简单的串行调用层，它们应该横向覆盖 Agent Runtime、Tool 和业务执行过程。

这七层能够比较清楚地回答：

- 客服业务功能在哪里实现？
- Agent 的决策和执行在哪里实现？
- 业务系统通过什么方式接入？
- 安全机制在哪里执行？
- 系统质量如何验证？

这比单纯的六大功能模块更适合指导技术研发。

# 四、这套系统的研发难度在哪里？

如果按照真实企业落地的标准，我会这样评估：

| 方向               | 技术难度 | 主要挑战             |
| ---------------- | ---- | ---------------- |
| 多渠道接入            | 中高   | 不同平台协议和消息机制      |
| 会话管理             | 中    | 上下文、身份关联、消息一致性   |
| 商品 RAG           | 中    | 知识切分、召回、准确性      |
| 智能导购             | 中高   | 商品筛选、推荐策略        |
| 订单 Agent         | 高    | 实时数据、业务状态        |
| 售后 Workflow      | 很高   | 状态机、幂等、异常恢复      |
| 多 Agent 编排       | 高    | 上下文、执行控制、协作      |
| 权限与安全            | 很高   | 多租户、数据隔离、操作授权    |
| Agent Evaluation | 高    | 场景构造、指标定义、执行轨迹评估 |

这里需要区分两种难度：

- Agent 技术难度：模型调用、Tool Calling、RAG、Agent Runtime、Workflow。
- 企业业务工程难度：真实 OMS、ERP、支付、物流系统对接，以及业务规则和数据权限。

后者往往比前者更难。

因此，不能认为接入一个大模型，再配置几个 Tool，就完成了企业智能客服系统。

# 五、如果将它作为一个实际项目，应该如何分阶段？

我不建议一开始就做全渠道、全业务、多 Agent 的完整系统。

可以按六个阶段推进。

| 阶段 | 建设目标          | 核心交付                           |
| -- | ------------- | ------------------------------ |
| P0 | 客服 Agent 基础设施 | 会话、Runtime、Tool Registry、Trace |
| P1 | 智能知识问答        | RAG、商品查询、FAQ、知识评估              |
| P2 | 订单与物流 Agent   | 订单查询、物流查询、工具调用                 |
| P3 | 售后业务自动化       | 退款申请、退换货、Workflow、审批           |
| P4 | 人机协同与运营       | 人工工作台、工单、质检、运营分析               |
| P5 | 企业级治理与扩展      | 多租户、权限、安全、Evaluation、渠道扩展      |

每个阶段都应该有独立的验收标准，而不是只以功能是否开发完成作为标准。

例如 P3：

- 退款资格判断正确。
- 不符合条件的退款不能提交。
- 重复请求不会产生重复退款。
- API 超时后能够查询和恢复任务状态。
- 用户确认和实际退款结果能够区分。
- 整个执行链路能够追踪。

这些才是企业级 Agent 项目的有效验收标准。

# 六、最终评价：这份设计适不适合作为一个 Agent 工程项目？

我认为适合，但要明确你想通过它证明什么。

结合你之前关注的 Harness Engineering、企业 Agent 工具调用、执行链路可靠性和 Agent Evaluation，我建议重新考虑这个项目的定位。

不要把重点放在做一个功能齐全的电商客服产品，而应该放在：

构建一个具备业务执行能力、可靠性保障和质量评估体系的企业级 Customer Service Agent。

原因有三个：

1. 电商客服是一个容易理解的业务场景，能够自然引出 RAG、Tool Calling、Workflow、多轮对话和人工审批。
2. 退款、改址、取消订单等操作能够体现 Agent 从回答问题到执行任务的区别。
3. 可以通过模拟 OMS、物流、支付等业务系统，构造大量真实工程故障，验证 Harness 的价值。
