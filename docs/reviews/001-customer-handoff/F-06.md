## Spec 轴报告

首轮 6 条（0 阻塞），逐条处理：

1. **[建议 → 保留为 plan 澄清]** plan 5.1 越权矩阵写“队列摘要：客户 403”，但客户 cookie 访问 `/workspace/queue` 实际为 401（无 employee cookie 即未认证）。按 F-05 语义，客户 cookie 不构成员工认证上下文；F-05/AC-34 的 403 特指“合法员工凭据但角色非 agent”。实现保留 401，登记为 plan 澄清项，不在本卡引入跨认证耦合。
2. **[接受为后续]** plan 3.3.5 只写“脱敏末条/等待秒数”，未定义末条作者与等待起算点；当前口径由执行卡 D-2/D-3 固定（最后一条客户消息；请求时刻减 `created_at` 向下取整、负数夹 0）。不改已批准 plan，后续 spec 迭代时回写。
3. **[建议 → 已整改]** `order_count` 原从 `handoff.context` 派生，脏 context 非 0 会外显；plan 3.3.5 明确 `order_count=0`。已固定返回 0，并新增 `context=7` 仍返回 0 的用例。
4. **[接受]** 同 `created_at` 按 UUID 字符串 id 升序只保证确定性，不反映真实先后；plan 3.3.5 已指定 `created_at, id` 双键，F-07 演示时需注意同秒场景。
5. **[建议 → 已整改]** `distinct_on` 仅 SQLAlchemy 2.1 提供，而 pyproject 声明 `>=2.0.36`。已改为相关标量子查询，兼容声明下限并保持“只取一条”。
6. **[接受]** 等待秒数只在加载时渲染、不随时间刷新；执行卡 D-8 明确不轮询，AC-35 未要求。

Scope creep 核对：新增内容仅为队列展示样式、加载/重试/空态文案、`readError` 导出与 OpenAPI 契约同步，未扩大业务范围。增量复核：2 条关闭、4 条保留且均非阻塞，**未发现新的规格偏差**；并提示 002 接入订单后需重新对照 plan 3.3.5 的 `order_count`。
