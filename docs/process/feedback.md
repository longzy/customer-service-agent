# 反馈与复盘

- 状态：草案（2026-11-22，随 P0/P1/P2 落地；用户确认后转已批准）
- 用途：把门禁失败与运行/评测结果变成规则、测试或规格变更，避免同类问题重复。
- 关联：[WORKFLOW](WORKFLOW.md)、[评审 checklist](review-checklist.md)、[评测说明](../../evals/README.md)

## 两个环

### 环 A：门禁 → 规则/测试

触发：全量/定向测试红、评审阻塞、收口被 `close_feature.py` 拒绝、mutation 低于阈值。

处理（每 feature 收口时 5–10 分钟）：
1. 归类：测试缺失、规则缺失、规格歧义、环境/工具缺陷。
2. 选择动作：补测试、补机械检查（lint/脚本/CI）、改规格、或登记为后续任务；
   评审记录的 `## 0.1 条件项分类` 是输入——「机械」项必须转成检查，「判断」项留评审。
3. 写回：执行卡 §4 / 评审记录「整改回应」；后续项必须写承接 feature。
4. 只有“规则有强制点”才写入 `standards.md`；否则留作判断项。

### 环 B：运行/评测 → 规格

触发：eval 失败/漂移、岗位走查差异、线上事故（M1 后）。

处理：
1. 用 [复盘模板](../templates/postmortem.md) 记录时间线、影响、根因。
2. 每个行动项指定 owner、截止、类型（测试/规则/规格/任务）。
3. 规格变化回到 `requirements.md`/`design.md`，不直接改代码绕过 AC。
4. 真实模型质量在 M1 只做趋势，不进硬门禁；进入门禁前按 T3 决策。

## 指标

`python3 scripts/gate_metrics.py` 读取评审记录与最近评测报告：

| 指标 | 用途 |
|---|---|
| 评审结论分布 | 有条件通过/不通过是否集中 |
| T3 安全评审覆盖 | `close_feature` 门禁是否被绕过 |
| 「接受为后续」数量 | 后续项是否有人承接 |
| 最近评测 failed/skipped | JUnit 是否被跳过或红 |
| AC 覆盖与待开工 | 追溯基线是否过期 |

补充人工指标（月度）：
- 全量门禁一次通过率、平均评审耗时、flaky 测试数；
- 逃逸缺陷（收口后才发现）与对应缺失门禁；
- mutation 分数与未达标模块。

## 节奏

- **每 feature**：收口时 `make verify` 自动回填评审记录，随后跑 `make metrics`；有失败/阻塞或机械项则做环 A 记录。
- **每月**：汇总指标，挑 1 个最高频问题改成机械检查或测试；不新增无强制点的规则。
- **每季度**：检查 `docs/process/` 是否有重复/过期规则，删除或合并。
