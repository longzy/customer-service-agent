# Spec 开发规范

- 状态：已批准
- 批准：2026-11-14（本次会话由用户确认）
- 日期：2026-11-14
- 适用：本仓库所有里程碑与变更
- 关联：`docs/process/README.md`（任务闭环）、`docs/process/tdd.md`（测试先行与突变检查）、`docs/architecture/invariants.md`（硬约束）

## 给非实现者的速览

- **一个变更一个目录**：M1 的订单取消在 `docs/specs/M1/001-order-cancel/`；以后每个新功能一个编号目录。
- **门禁**：需求没批准不写设计，设计没批准不排任务，任务没写清不写代码。
- **检查器**：提交前自动跑 `scripts/check-docs.py`，缺文件、编号重复、依据未批准都会直接失败。

## 1. 目的

把"规格 → 设计 → 任务 → 实现 → 评审"的产物固定在可预测的路径上，使人和 Agent 都不需要猜文件在哪、也不需要判断某份文档是否够用。路径与必需文件由检查器强制执行，不依赖记忆。

三条原则：

- 一个变更一个目录：规格目录对应一次可独立验收的变更，不按技术分层组织。
- 先设计后分解：任务地图在需求与设计批准之后产生；执行细节在任务开工前就近展开。
- 文档即契约：缺少必需文件、状态越级、依据未批准，检查器直接失败。

## 2. 固定路径

```text
docs/
  product/charter.md              产品定位与范围
  architecture/                   总体架构与不变量
  adr/                            架构决策记录
  specs/<M>/<NNN>-<slug>/         一个变更一个目录
    requirements.md               需求与用户故事（必需）
    design.md                     技术设计（必需）
    acceptance.md                 验收用例（必需）
    tasks.md                      任务地图（必需）
    clarifications.md             澄清清单，可为空但必须存在（必需）
    ui.md                         界面与交互（涉及界面时必需）
    ui-mockup.html                结构参考稿（可选）
  tasks/<NNN>-<slug>/T-XX.md      任务执行卡，与 spec 目录同名
  design-system/                  设计令牌与组件契约
  process/                        协作流程与本文
  research/ handoffs/ reviews/ templates/ CURRENT.md
```

命名规则：

- `<M>` 为里程碑标识，例如 `M1`。
- `<NNN>` 为三位递增编号，在同一里程碑内唯一且不复用。
- `<slug>` 为小写英文短语，用连字符分隔，与变更名对应。
- 执行卡编号 `T-XX` 与 `tasks.md` 中的任务编号一致。

## 3. 阶段与门禁

| 阶段 | 产物 | 门禁 |
|---|---|---|
| 需求 | `requirements.md` + `clarifications.md` | 澄清条目清零，需求才可批准 |
| 设计 | `design.md`、`ui.md`、`docs/design-system/` | 需求已批准，且设计中的未决项全部关闭 |
| 任务地图 | `tasks.md` | 设计已批准；每个任务可追溯到 AC 或声明基座豁免 |
| 执行卡 | `docs/tasks/<spec>/T-XX.md` | 依据文档已批准；4.1 需人类决策为空或已答复；seam 已写明 |
| 实现 | 代码、测试 | 按 `docs/process/tdd.md` 红-绿推进；执行卡完成标准逐条满足，验证输出留痕 |
| 评审 | `docs/reviews/<spec>/T-XX.md` | 由未参与实现的上下文执行；执行卡标记完成前必须有评审记录 |
| 记录 | `CURRENT.md` | 与本次变更同一次提交 |

门禁的判定方式是检查器，不是会议。

## 4. 状态与生命周期

规格类文档只使用四个状态：`草案` → `等待评审` → `已批准`，以及 `拟议`（仅 ADR）。

- 批准必须记录日期与来源。
- 已批准文档的修改必须留下变更记录：改需求或验收写回本文件；改架构写新 ADR。
- 执行卡使用 `待确认`、`待开工许可`、`已完成`，且只有 `待开工许可` 与 `已确认` 会触发依据检查。
- 标记 `已完成` 的前提包括：红-绿证据已记录；自 T-07 起，关键模块突变分数达标。

## 5. 执行卡与任务地图的分工

- `tasks.md` 只回答顺序、依赖与 AC 追溯，粒度到"能排序、能追到 AC"。
- 执行卡回答这次改动到底做什么、完成标准是什么、哪些决定归人类。
- 任务开工时允许修正 `tasks.md` 描述，但必须在同一次提交内更新并说明理由。

## 6. 检查器覆盖的规则

`scripts/check-docs.py` 在提交前执行，覆盖：

- 内部链接可解析。
- 文档状态词合法。
- `CURRENT.md` 含规范第 5 节要求的全部字段。
- 每个规格目录命名符合 `NNN-slug`，编号在同里程碑内唯一。
- 每个规格目录具备必需文件。
- 每条 AC 至少被 `tasks.md` 引用一次。
- 执行卡目录与规格目录同名；状态开放时其依据文档必须已批准或已清零。
- 标记为已完成的执行卡必须有评审记录 `docs/reviews/<spec>/T-XX.md`，且记录包含结论。

## 7. 与外部工具的关系

不引入 `.specify/`、`.kiro/` 或同类工具的目录与命令：本仓库已用 `AGENTS.md` 做路由、`CURRENT.md` 做实时状态、git hook 做门禁。再叠加一套仪式会产生第二个权威。

## 8. 变更控制

- 规格范围变化：更新 `requirements.md` 与 `acceptance.md`，重新评审。
- 架构取舍变化：新增 ADR，保留旧决策与替代原因。
- 目录或命名规则变化：先改本文，再改检查器，最后迁移文件；三者顺序不得颠倒。
