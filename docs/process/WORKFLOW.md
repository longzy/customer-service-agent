# 标准开发工作流（SDW）

- 状态：已批准
- 批准：2026-11-16（本次会话由用户确认）
- 日期：2026-11-16
- 适用：本仓库全部变更；人类开发者与 AI Agent 同权
- 关系：本文定义“工作怎么流动”；[工程标准](standards.md) 定义“什么算合格”；[架构不变量](../architecture/invariants.md) 定义“什么不能破”
- 依据：[开发规范评审](../reviews/2026-11-16-dev-standards-review.md)

## 0. 一页速览

```text
登记 → 分级 → 规格 → 设计 → 任务地图 → 执行卡 → 红-绿 → 验证 → 独立评审 → 记录/发布
 S0     S0     S1     S2      S3          S4      S5      S6        S7          S8
```

三条默认规则：

1. **门禁按风险配比**：改错别字和改权限模型不该走同一套流程。
2. **服务端 CI 是唯一硬门禁**：本地 hook 只负责“早发现”，不负责“算数”。
3. **状态由产物派生**：`CURRENT.md` 是视图，不是手写日志；任何人工副本都要能被脚本核对。

## 1. 设计原则

| ID | 原则 | 反例（本仓库实际出现过） |
|---|---|---|
| P-1 | 风险配比：门禁强度与“改错的代价”成正比 | 所有任务都要求突变分数、独立评审、5 份文档 |
| P-2 | 机器优先：能机器判定的规则不写进人脑 | `oms_timeout_seconds` 未接入，只靠人记 |
| P-3 | 单一事实源：同一事实只有一个可写位置，其余派生 | `CURRENT.md`/`tasks.md`/执行卡/评审 4 份状态副本 |
| P-4 | 证据可复现：证据 = 命令 + commit + CI 产物，不是粘贴文本 | 卡内贴 `76 passed`，评审记录写 `82 passed` |
| P-5 | 规则预算：每条规则有 owner、强制点、失效期；新增必须替换或删除一条 | 状态词在 3 份文档各写一遍 |

## 2. 变更分级

分级在 S0 由实现者提出、由门禁脚本或评审确认；**分级错误本身是流程缺陷**，应在回顾中修正判据。

| 级别 | 判据（满足任一即升级） | 产物 | 评审 | 门禁 |
|---|---|---|---|---|
| **T0 微改** | 注释、文档措辞、格式、依赖补丁（无 API/行为变化） | 无卡 | 自审 | G0 + G2 |
| **T1 常规** | 单个可观察行为；不动契约、迁移、权限、依赖 | 执行卡 + 评审记录 | 1 名独立评审 | G0–G2 + G3（命中模块时） |
| **T2 结构性** | 跨层行为；契约/迁移/新依赖/新模块；性能或数据模型变化 | 更新 spec/design；必要时 ADR；执行卡 | 2 名（含领域 owner） | G0–G3 + 迁移回滚演练 |
| **T3 高风险** | 权限/租户/资金/不可逆操作/生产基础设施/模型与 Prompt 变更 | 全部 + 威胁建模 + 回滚预案 + 灰度方案 | 独立安全评审 + 业务负责人批准 | G0–G4 + 封存评测阈值 |

默认取 T1。降级必须写理由；**升级不许省**——拿不准时按高一级处理。

## 3. 阶段

### S0 登记与分级

- 输入：用户目标或 Issue。
- 动作：分配变更编号（`NNN-slug`，不复用）；判定 T0–T3；确认是否在 `docs/roadmap.md` 的里程碑范围内。
- 产物：变更目录（T1+）或直接提交（T0）；分级结论写入卡或提交说明。
- 门禁：不在里程碑范围内 → 停止并请求决策（见 `AGENTS.md` 的停止条件）。
- 失败处理：范围不清先澄清，不进 S1。

### S1 规格（requirements）

- 产物：`requirements.md`，含用户故事、EARS 功能需求、验收标准（AC）、非目标、假设。
- 门禁：每条 FR 至少被一条 AC 覆盖；AC 编号连续唯一；澄清项清零；状态 `已批准` 才能进 S2。
- 完成标准：一个不了解背景的人能只读本文写出测试。
- 失败处理：证据不足且错判有资金/隐私/合规风险 → 转人工决策，不猜。

### S2 设计（design）

- 产物：`design.md`，含组件边界、时序、契约、数据模型、错误映射、测试策略、界面、未决项。
- 门禁：`design.md` 未决项为空；影响架构取舍 → 新增 ADR；接口字段进契约文件。
- 完成标准：接口、状态迁移、失败路径都有唯一定义位置。
- 失败处理：设计与不变量冲突 → 停止实现，先改设计或 ADR。

### S3 任务地图（tasks）

- 产物：`tasks.md`，按垂直切片；每个任务能排序、能追到 AC。
- 门禁：每个任务有 ID、依赖、`_验收:` 行；AC 全覆盖。
- 完成标准：任务粒度是“一个可观察行为”，不是“一层代码”。

### S4 执行卡（仅 T1+）

- 产物：`docs/tasks/<spec>/T-XX.md`，绑定 ≤2 个 AC；写明改变范围、人类决策、seam、失败矩阵、验证命令。
- 门禁：依据文档已批准；2.1「需人类决策」为空或已答复；超 2 个 AC 必须拆分或书面说明。
- 完成标准：实现者不需要再猜需求。

### S5 红-绿

- 动作：一次一个场景——先写失败测试并保留输出，再写刚好通过的最小实现。
- 门禁：卡第 4 节有红-绿输出；禁止 horizontal slicing；测试名含 `_AC_XX`。
- 完成标准：新增行为有测试，失败路径可达。

### S6 验证

- 动作：`./scripts/verify.sh`；命中关键模块时跑 `./scripts/mutation.sh`。
- 门禁：G0–G2 全绿；集成测试不允许静默跳过；证据写入卡第 4 节（命令 + 计数 + commit）。
- 完成标准：命令与结果可被第二个人复现。

### S7 独立评审

- 要求：评审者未参与实现；只看“diff + 规格 + 不变量”，先盲评再对答案。
- 门禁：评审记录逐 AC 给结论；结论只能是 `通过` / `有条件通过` / `不通过`；阻断项必须闭合。
- 完成标准：每个 AC 都有“实现证据”或“明确未完成说明”。

### S8 记录与发布

- 动作：更新 `tasks.md` 勾选与卡状态；运行 `check-status.py`；按需生成 CHANGELOG 与版本号。
- 门禁：状态三方一致；发布说明与提交类型一致；迁移可回滚。
- 完成标准：新会话只读仓库即可继续。

## 4. 门禁阶梯

| 层 | 触发 | 时限 | 内容 | 权威性 |
|---|---|---|---|---|
| **G0** | `pre-commit` | ≤ 5s | 格式、lint、类型（增量）、文档结构、状态一致性、追溯矩阵、secret 扫描 | 反馈 |
| **G1** | `pre-push` | ≤ 2min | 单测 + 集成（独立测试库）+ 路由覆盖 + 文档 | 反馈 |
| **G2** | PR / push 到 `main` | ≤ 10min | G1 + 生产构建 + 依赖审计 + SAST + 覆盖率（diff） | **唯一硬门禁** |
| **G3** | 夜间 | ≤ 30min | 突变检查、契约测试、E2E、flaky 检测 | 趋势 + 阻断发布 |
| **G4** | 发布 | 人工 | 迁移演练、回滚演练、评测阈值、变更说明 | 发布审批 |

必备 required checks（服务端）：

1. `verify.sh --no-record` 全绿（当前 20 秒级，可支撑每次 PR）。
2. `scripts/trace.py --strict` 无未登记缺口。
3. `scripts/check-status.py` 通过。
4. 前端生产构建通过。
5. 依赖审计与 secret 扫描无高危。

绕过规则：禁止 `--no-verify` 直接推送；确需热修复时在 PR 描述写明原因，并在 24 小时内补跑完整门禁。

## 5. 状态与追溯

### 5.1 状态的唯一事实源

| 事实 | 唯一写入位置 | 派生视图 |
|---|---|---|
| 任务是否完成 | `docs/specs/<spec>/tasks.md` 的复选框 | `CURRENT.md` 的已完成/下一步 |
| 任务的执行契约 | `docs/tasks/<spec>/T-XX.md` | 评审记录 |
| 评审结论 | `docs/reviews/<spec>/T-XX.md` | 卡的状态 |
| 最近验证 | `verify.sh` 生成的标记块 | 无 |

规则：

- `CURRENT.md` 只保留“一页索引 + 当前决策”，不再记录历史过程。
- `scripts/check-status.py` 校验三方一致；不一致时先修事实，不改叙述。
- 任何“已交付”声明必须能追到 `tasks.md` 勾选 + 卡状态 + 评审记录三者。

### 5.2 AC 追溯

- AC ID 是追溯骨架：`requirements.md` 定义 → `tasks.md` 引用 → 测试名内嵌 `_AC_XX` → 评审逐条结论。
- `scripts/trace.py` 生成矩阵；未覆盖的 AC 必须登记在 `scripts/trace-baseline.txt` 并写明承接任务。
- 基线只减不增；基线项一旦被覆盖，必须删除该行，否则门禁失败。

## 6. AI 协作规则

### 6.1 上下文预算

| 文件 | 上限 | 说明 |
|---|---|---|
| `AGENTS.md` | 60 行 | 只放路由与硬边界 |
| `CURRENT.md` | 80 行 | 一页状态 |
| 单份 process 文档 | 300 行 | 超限拆分为索引 + 分册 |
| 执行卡 | 120 行 | 接口细节放 `design.md` |

加载顺序固定：`AGENTS.md` → `CURRENT.md` → 任务相关 spec/ADR/卡。不相关文档不加载。

### 6.2 Agent 必须做

- 开工前复述：阶段、已完成、进行中、阻塞、下一步。
- 先写失败测试，再写实现；保留红-绿输出。
- 每个结论给出证据：文件行号、命令、退出码。
- 发现文档与代码冲突：先报告，不自行选择更方便的解释。
- 结束前更新事实源（`tasks.md`/卡/`CURRENT.md`），并跑 `verify.sh`。

### 6.3 Agent 禁止做

- 自审自签（实现者不得撰写自己的评审结论）。
- 修改 `docs/architecture/invariants.md` 的语义、跳过门禁、编造 AC。
- 未经批准引入新依赖、新服务、新存储。
- 把密钥、真实用户数据、生产配置写入仓库或日志。
- 用“测试通过”代替“行为正确”的论证。

### 6.4 AI 生成代码的三项额外证据

| 证据 | 检查方式 | 失败案例 |
|---|---|---|
| 依赖真实存在 | 锁文件 / 包管理器解析成功 | 幻觉包名（USENIX 2025：商用模型 5.2%） |
| 许可证可接受 | 依赖清单 + 许可证扫描 | 引入 GPL 到闭源产品 |
| 测试能自证 | 反向验证 + 突变分数 | 断言复算实现、mock 内部协作者 |

### 6.5 停止并请求决策

沿用 `AGENTS.md` 的停止条件，另加三条：

- 需要把 T1 临时降为 T0 才能按时交付。
- 需要跳过 G2。
- 发现不变量与业务需求直接冲突。

## 7. 评审标准

### 7.1 六问（所有级别）

1. 契约等价：是否复用 `packages/contracts`，而不是另建一套？
2. 测试自证：改坏一处实现，测试会不会失败？
3. 失败路径可达：超时、非法响应、越权是否真的到达出口？
4. 证据可复现：命令、计数、commit 是否齐全？
5. AC 可追溯：每个 AC 是否有通过或明确未完成的结论？
6. 未声明的 seam：是否驱动了卡里没声明的内部接口？

### 7.2 分级附加

| 级别 | 附加检查 |
|---|---|
| T2 | 迁移可回滚；契约变更前后兼容；性能影响有数字 |
| T3 | 威胁模型；越权矩阵；回滚与灰度预案；评测集通过率 |

### 7.3 输出格式

```text
- 结论：通过 / 有条件通过 / 不通过
- 逐 AC：AC-01 通过（证据）| AC-18 未完成（原因 + 承接任务）
- 阻断项：编号 + 位置 + 必须修复的内容
- 非阻断项：编号 + 建议
```

首轮评审在 24 小时内给出；阻断项修复后必须有一轮复核记录。

## 8. 发布与版本

- 提交：Conventional Commits（`feat`/`fix`/`docs`/`refactor`/`test`/`chore`），范围用任务号或模块名。
- 版本：SemVer；`feat` → MINOR，`fix` → PATCH，`BREAKING CHANGE` → MAJOR。
- 变更日志：由提交类型生成草稿，人工润色；对外版本遵循 Keep a Changelog 结构。
- 数据库：expand → migrate → contract；每次迁移必须有 `downgrade` 与回滚演练记录。
- 发布物：CI 产物（镜像/包/SBOM）+ 版本号 + CHANGELOG + 迁移说明。

## 9. 度量与回顾

| 指标 | 采集方式 | 用途 |
|---|---|---|
| 变更前置时间 | 首个 commit → 合并 | 发现流程瓶颈 |
| 部署频率 | 合并到 `main` 的次数 | 判断批次大小 |
| 变更失败率 | 回滚/热修复数 ÷ 发布数 | 门禁是否有效 |
| 恢复时间 | 故障开始 → 恢复 | 可观测性是否够 |
| 评审轮次/返工率 | 评审记录轮次 | 判断规格质量 |
| 门禁绕过次数 | `--no-verify` 审计 | 判断门禁摩擦 |
| 文档漂移数 | `check-status.py` 问题数 | 判断治理成本 |

回顾节奏：每 10 个任务或每两周一次。**回顾的产出必须是“改一条门禁”或“删一条规则”**，不接受只写感受。

## 10. 落地路线

| 周 | 交付 | 完成判据 |
|---|---|---|
| W1 | CI + required checks；`verify.sh` 闭合；测试库隔离；状态/追溯检查 | PR 未过 CI 无法合并 |
| W2 | 本工作流 + 工程标准获批；规则副本收敛 | 同一规则只剩一个写入位置 |
| W3 | `CURRENT.md` 自动生成；链接与路径全量校验 | 无人手工编辑状态页 |
| W4 | 覆盖率（diff）、夜间突变、E2E、评测集 | 四个指标有连续 2 周数据 |

与现有文档的迁移映射：

| 现有文档 | 目标 |
|---|---|
| `docs/process/README.md` | 任务闭环并入本文 S0–S8，保留工具切换与安全边界 |
| `docs/process/sdd.md` | 阶段与门禁并入本文第 2–4 节，路径规则保留 |
| `docs/process/tdd.md` | 测试策略并入 [工程标准](standards.md) STD-TEST-*，突变阈值保留 |
| `docs/process/review.md` | 并入本文第 7 节 |

迁移顺序：先批准本文 → 再改指针 → 最后删除旧文档；三者不得颠倒。

## 11. 规则预算（防膨胀）

- 新增规则必须回答：谁执行、在哪强制、违反时发生什么、什么时候失效。
- 没有强制点的规则，只能写成“建议”，不得写成“必须”。
- 每条规则有 owner；连续两个季度无违反记录的规则，评估删除。
- 每次回顾最多新增 2 条规则，且必须删除或合并至少 1 条。
