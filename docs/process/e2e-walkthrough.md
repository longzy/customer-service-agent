# 端到端/浏览器走查配方

- 状态：已批准
- 批准：2026-11-18（用户要求落地 retro 改进）
- 适用：需要真实浏览器验证的任务；具体步骤以执行卡第 3、4 节为准

## 1. 为什么需要配方

M1 的客户与员工认证都基于 cookie。**同一浏览器上下文的标签共享 cookie**：在第二个标签登录 `customer_b` 会把 `customer_a` 的会话顶掉；未登录状态也无法在已登录的上下文里模拟。走查前先决定身份隔离方式，否则会得到错误结论。

## 2. 身份隔离

按可信度从高到低：

1. **每个身份一个独立浏览器 profile / 无痕上下文**：最接近真实双浏览器，优先。
2. **一个浏览器 + 一个 API 客户端**：浏览器验证 UI 主路径；另一个身份用独立 cookie jar 调 API 制造数据（例如第二个客户转人工）。
3. **同一浏览器登出后切换身份**：只适合“先后发生”的场景。登出会撤销 session，但**不会删除已入队的交接单**；记录这一点，避免误判数据丢失。

未登录 401 用不带 cookie 的 API 客户端验证，不要用已登录浏览器的标签“假装未登录”。清理 cookie 前先读所使用浏览器工具的 cookie 清理说明，避免清掉整个 profile。

## 3. 走查顺序

```bash
make dev-reset ARGS=--yes   # 干净演示数据
make dev ARGS=--no-install  # 非交互环境可跳过依赖安装
```

1. 客户 A 登录 → 触发目标行为（如“转人工”）→ 记录状态与可见文案。
2. 客户 B 用隔离方式重复，确认两个身份的数据独立。
3. 坐席登录 → 确认队列/会话/摘要/越权 404 或 409。
4. 用 API 或另一浏览器补验未登录 401、跨租户/他人资源 404。
5. 走查后 `make dev-reset ARGS=--yes` 恢复干净数据，`make dev-stop` 停止 3000/3001/8000。

## 4. 证据

- 截图/录像放 `evals/reports/<spec>/F-XX/`（该目录已 gitignore），不要只留 `/tmp`。
- 证据写：命令、可观察结果、截图相对路径、commit。
- 浏览器无法覆盖的 401/并发分支，明确写“由哪条集成测试覆盖”，不要含糊带过。
