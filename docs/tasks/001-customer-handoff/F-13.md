## 1. 改变范围

- 本卡交付的用户可感知行为（只能一个）：登录、转人工、领取、接管、回复、关闭、转回都留下不可改删的审计；401/403/429 是审计过的安全事件；客户登录/员工登录/客户消息超限返回 429；审计写失败时写操作整体回滚并返回 503。
- 涉及层：后端（审计模块、路由、错误处理、迁移）与集成测试；不涉及前端代码，但错误码枚举与 `/customer/messages` 的 429 声明会更新契约生成物。

- 本次改变：
  - `backend/platform/models.py`：新增 `ServiceAuditEvent`（`service_audit_events`，只读）。
  - `migrations/versions/0011_service_audit_events.py`：建表、`(journey_id, created_at)` 索引与拒绝 `UPDATE`/`DELETE` 的触发器。
  - `backend/audit/__init__.py`、`backend/audit/service.py`：`AuditRecord`、`AuditWriter` 协议、`SqlAuditWriter`、`AuditUnavailableError`、审计 metadata 允许清单与事件类型常量。
  - `backend/api/service_audit.py`：路由侧 `audit_or_503()`（同事务写入，失败回滚并 503）与安全事件写入；安全事件 `entity_id` 截断到 64，完整路径进 metadata。
  - `backend/domain/errors.py` / `backend/api/main.py`：注册 `AUDIT_UNAVAILABLE`（503）与安全事件审计钩子；`create_app()` 注入 `app.state.audit_writer`。
  - `backend/api/csrf.py`：Origin 拒绝的 403 也写 `forbidden` 安全事件（plan 5.1 的 CSRF 威胁模型）。
  - `backend/api/customer_routes.py`：客户登录/登出/发消息/AI 回复/关闭写审计；客户消息按 session 限速 30/min；登录失败/限速带账号，消息 429 带客户身份。
  - `backend/api/workspace_routes.py`：员工登录/登出/领取/接管/回复/关闭/转回写审计；角色不符的 403 带员工身份。
  - `packages/contracts/schemas/domain.json`、`packages/contracts/tools/openapi.json`、`packages/contracts/openapi.json`、`apps/*/lib/api-types.ts`、`tests/fixtures/openapi-r0-2.json`、`tests/fixtures/db-schema-r0-2.json`：重新生成。
  - `backend/conversations/customer_chat.py`、`backend/conversations/handoffs.py`：`ChatResult` 携带新建交接单标识，客户消息转人工时写 `handoff.created`（与消息同事务）。
  - `backend/identity/customer_sessions.py`、`employee_sessions.py`：`Resolved*Session` 暴露 `session_id` 供限速桶键使用；登出只留 flush 的撤销函数，便于与审计同事务提交；`ForbiddenRoleError` 携带已知员工标识供 403 审计。
  - `tests/integration/test_service_audit_AC_39.py`：AC-39 集成用例（20 条）。
  - `tests/integration/customer_support.py`、`workspace_support.py`：清理时 `TRUNCATE service_audit_events`（行级改删被触发器拒绝）。
  - `scripts/trace-baseline.txt`：删除 AC-39 条目。
  - `docs/specs/001-customer-handoff/features.md`、`docs/CURRENT.md`：收口时更新。
- 本次不改变：
  - 会话/交接单状态机与既有错误码；不新增业务端点、不新增响应字段。
  - 既有登录限速键与窗口（`customer_login:{username}:{ip}`、`employee_login:{username}:{ip}` 5/15min）。
  - 旧 M1-P `audit_events` 表与 `backend/api/audit.py` 的取消流程审计。
  - 前端代码：审计/限速只体现在既有 429/503 封套，工作台与客户页不改。
  - 审计保留期、归档与清理任务（归 005 安全硬化）。
  - 24h 空闲自动关闭的 `conversation.closed` 审计：AC-39 场景未含系统自动关闭，登记到后续（见 §7）。

### 2.3 实现者自行决定

| ID | 问题 | 决定 | 理由 | 返工代价 |
|---|---|---|---|---|
| D-1 | 审计事件名 | 采用 plan 5.1 清单：`customer.login/logout`、`employee.login/logout`、`handoff.created/claimed`、`conversation.taken_over`、`message.replied`、`conversation.closed`、`conversation.returned_to_ai`、`auth.failed`、`rate_limited`、`forbidden`；另补 `message.sent`（客户消息）与 `ai.replied`（AI 回复） | plan 3.4 要求“客户发消息 message + audit”“AI 回复 AI message + ai_event + audit”，5.1 清单漏列；两者只记 ID，不记正文 | 小 |
| D-2 | `actor_type`/`actor_id` | 客户 `customer`、员工 `employee`、AI 回复 `system/system`；未认证的 401/429 用 `anonymous`，但路由已知账号时把 `username` 写进 metadata；登录 401/429 带账号，角色不符的 403 带员工 id，认证后的消息 429 带客户 id | 审计要能区分动作人；认证之前的请求没有可信身份，不能凭空编造；已知主体时不应丢归因 | 小 |
| D-3 | 审计失败注入与 503 | `app.state.audit_writer` 可替换；`record()` 内的 `SQLAlchemyError` 统一转 `AuditUnavailableError`，路由 `audit_or_503()` 回滚并返回 503 `AUDIT_UNAVAILABLE` | 测试可在不制造数据库故障的前提下验证“审计失败 → 业务回滚”；真实故障同样走 503 | 小 |
| D-4 | 401/403/429 审计的提交边界 | 路由在抛出 `ApiError` 前用 `audit_security_event()` best-effort 写独立 session 并标记；`ApiError` handler 只补记未标记的请求。写失败只记日志，不改写原响应 | 这类请求没有可回滚的业务事务；若安全事件写失败也回 503，会把 401 变成 503，掩盖认证结果 | 小 |
| D-5 | 不可改删的实现层 | 迁移里建 `BEFORE UPDATE OR DELETE` 触发器，任何行级改删直接抛错；不提供删除 API | AC 要求“尝试改删→失败”；触发器覆盖应用/手工 SQL，测试清理改用 `TRUNCATE` | 小 |
| D-6 | 客户消息限速键 | 解析 session 后取 `session_id`，桶键 `msg:{session_id}`，30/min；限速先于消息写入 | plan 5.1 指定按 `customer_session`；登录轮换会换 session，天然重置桶 | 小 |
| D-7 | 审计 metadata 脱敏 | 审计模块自带允许清单（路径/方法/状态码/错误码/`conversation_id`/`handoff_id`/`message_id`/账号/状态），不含消息正文、密码、token、IP 以外字段 | 复用 `redact_event` 的全局白名单会把安全事件需要的 `path` 等丢掉；审计不应保存正文 | 小 |
| D-8 | `handoff.created` 的写入位置 | `create_handoff()` 返回是否新建，`ChatResult` 携带 `handoff_id`；路由在客户消息同事务写审计 | 转人工由服务层决定（关键词/模型/低置信），路由只做审计编排；复用既有 `ChatResult` 不新增响应字段 | 小 |
| D-9 | 登出审计事务 | 登出只保留 `revoke_*_session`（flush）；路由先解析身份、写审计、再撤销并一次 commit；删除无调用方的 `logout_*_session` | 保持“审计与业务写同事务”；无 cookie/失效 cookie 仍幂等成功且不写审计；删除会绕过审计的死代码 | 小 |
| D-10 | 旧原型审计表 | 继续保留 `audit_events` 供 M1-P 取消流程使用；本卡只新增 `service_audit_events` | 不把 M1-P 兼容债带回新表（plan 3.2 的选择） | 小 |
| D-11 | 安全事件实体长度 | `entity_id` 取 `request.url.path[:64]`，完整路径、方法、状态码、错误码、IP 放 metadata | 安全事件路径可超过列宽（`/workspace/conversations/{uuid}/messages`），不截断会 INSERT 失败并静默丢审计 | 小 |
| D-12 | Origin 拒绝的审计 | `csrf.py` 在返回 403 前调用同一个 `audit_security_event()`，写 `forbidden` | plan 5.1 把 CSRF/Origin 验证归 AC-39；中间件绕过 `ApiError` handler，不能只在 handler 补 | 小 |
| D-13 | 客户关闭 `from_status` | 关闭前先取 `conversation.status` 快照；条件 UPDATE 会同步 ORM 对象 | 审计要记录动作前状态，不能记成 `CLOSED → CLOSED` | 小 |
