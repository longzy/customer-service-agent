- 关联 feature：F-14
- 依据：`docs/specs/001-customer-handoff/requirements.md` AC-33；`docs/specs/001-customer-handoff/design.md` 3.3.1（会话/交接单状态机）、3.3.2（认证）、3.3.3（客户 API）、5.1（越权矩阵与威胁模型）；`docs/specs/001-customer-handoff/tasks.md` F-14
- 绑定验收：AC-33
- 变更级别：T3（跨客户隔离与端到端安全验收；不新增生产接口、不改状态机）
- 设计引用：隔离口径以 plan 3.3.3 的 `GET /customer/conversations/{conversation_id}`（他人/不存在 404）与 5.1 越权矩阵为准；本卡不重复描述既有设计

## 1. 改变范围

- 本卡交付的用户可感知行为（只能一个）：客户甲、客户乙都能完整走登录 → 聊天 → 转人工 → 被接管 → 坐席回复 → 转回 AI → 再次转人工 → 关闭；甲读乙的会话/消息一律 404，两人的会话与交接单互不串。
- 涉及层：集成测试；生产代码预计不改（若测试暴露隔离缺口，按 plan 3.3.3/5.1 修复并回写本卡）。

- 本次改变：
  - `tests/integration/test_customer_isolation_AC_33.py`（已创建）：AC-33 端到端集成用例（含双坐席、消息负向探针）。
  - `scripts/trace-baseline.txt`：收口时删除 AC-33 基线条目（实现期保留，`trace.py` 按 Passes=false 判部分覆盖）。
  - `docs/specs/001-customer-handoff/tasks.md`、`docs/STATUS.md`：收口时更新。
- 本次不改变：
  - 生产 API、状态机、权限模型、数据库结构；不新增端点/字段/迁移。
  - 前端：AC-33 的前端走查由 F-14 的 `Steps` 手工执行，应用代码不动。
  - 审计/限速：由 F-13/AC-39 覆盖，本卡不重复断言。
  - 并发领取、关闭/转回幂等：分别由 AC-35/AC-38 覆盖，本卡只验证双客户交错下的隔离。

### 2.2 声明的 seam

| ID | 内部接口 | 为什么测试直接驱动它 |
|---|---|---|
| S-1 | `POST /customer/sessions`、`GET /customer/session` | 两个客户各自登录并拿到独立会话 |
| S-2 | `POST /customer/messages`、`GET /customer/messages?after_id=` | 聊天、转人工、客户轮询看到接管/回复、关闭后 409 |
| S-3 | `GET /customer/conversations/{conversation_id}` | 甲读乙会话 404、不存在 404、本人读取 200 |
| S-4 | `GET /workspace/queue`、`POST /workspace/queue/{id}/claim` | 两张独立交接单、按客户账号定位、互不抢占 |
| S-5 | `POST /workspace/conversations/{id}/takeover`、`POST .../messages` | 被接管、坐席回复，且只作用于目标客户 |
| S-6 | `POST /workspace/conversations/{id}/return-to-ai`、`POST .../close` | 转回 AI 后同一会话继续；坐席关闭只关目标会话 |
| S-7 | `service_conversations`、`service_handoffs` 表 | 断言归属（customer_id/conversation_id）与每人交接单独立 |

### 2.3 实现者自行决定

| ID | 问题 | 决定 | 理由 | 返工代价 |
|---|---|---|---|---|
| D-1 | 是否需要新增生产接口 | 不新增；AC-33 的隔离由既有 ownership 查询与 404 满足 | plan 3.3.3 已规定；端到端用例先验证，暴露缺口再按同一契约修复 | 小 |
| D-2 | “甲读乙消息”的验证口径 | `/customer/messages` 无 `conversation_id` 参数，按当前登录客户解析会话；用四层断言：(a) 甲带乙 `conversation_id` 读会话 404；(b) 甲轮询只返回甲消息；(c) 伪造 `conversation_id` 查询参数、带 `conversation_id` 的写请求（422）、`GET /customer/conversations/{乙}/messages`（404）都不能读到乙；(d) 用乙的消息 id 作 `after_id` 仍不含乙正文 | 不为了测试新增按 id 读消息的接口；四层合起来覆盖“读不到乙的消息” | 小 |
| D-3 | 每个客户是否都走“转回 + 关闭” | 是。每个客户完整走：转人工 → 接管 → 回复 → 转回 AI → 再转人工 → 再接管 → 关闭 | AC-33 要求甲/乙都能完整走关闭、转回；两轮也顺带验证同会话新交接单 | 中（重写用例） |
| D-4 | 关闭者分配 | 甲由客户自己关闭，乙由坐席关闭；两种关闭路径都在 AC-33 内可见 | 同时覆盖客户关闭与坐席关闭，不重复 F-11/F-12 的专项断言 | 小 |
| D-5 | 测试数据来源 | 全部通过公开 API 生成（登录/发消息/领取/接管/回复/转回/关闭），不直接播种会话或交接单 | AC-33 是端到端验收；播种会绕过登录与转人工路径 | 小 |
| D-6 | 模型 | 注入 `FakeModelClient`，按消息精确返回；关键词“转人工”不调用模型 | 与 AC-31/32 的测试约定一致，避免真实模型不确定性 | 小 |
| D-7 | 双客户与双坐席形态 | 两个客户各一个 `TestClient`（独立 cookie jar）；甲由 `agent_1`、乙由 `agent_2` 处理；第二坐席对甲会话读 404、重复领取 409 | plan 5.2 的 AC-33 seam 是“2 客户/2 坐席”；AC-33 同时验证同租户越权 | 小 |
| D-8 | 双浏览器走查的身份隔离 | 同一浏览器两个 host：`localhost:3000`（甲）与 `127.0.0.1:3000`（乙）；cookie 按 host 隔离，工作台 `localhost:3001`。这不是两个独立浏览器上下文，但满足 AC-33 所需的会话隔离与双身份 UI 走查；作为 features Steps 的等价替代，由 Spec 增量复核接受 | ego-browser 的 TaskSpace 共享 profile cookie；两个 host 是同一工具内可验证的隔离方式，且比 API 客户端更接近 Steps | 小 |
