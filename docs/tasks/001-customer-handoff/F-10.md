## 1. 改变范围

- 本卡交付的用户可感知行为（只能一个）：坐席在已接管（`HUMAN_ACTIVE`）会话里回复，客户下一次 3s 轮询看到该消息；客户在人工中发的消息进入工作台实时消息流，且不再触发 AI。
- 涉及层：后端（服务 + API）、契约（OpenAPI 与两个前端类型）、前端（仅 `apps/workspace`；`apps/chat` 已具备 3s 轮询与 `agent` 消息渲染，不改）。

- 本次改变：
  - `backend/conversations/workspace_conversations.py`：新增工作台消息读模型与回复写模型（归属校验、`HUMAN_ACTIVE` 才可写、幂等重放、同事务更新会话活跃时间）。
  - `backend/api/workspace_schemas.py`：新增 `AgentMessageRequest`（正文 1–500、去首尾空白、拒绝未知字段）。
  - `backend/api/workspace_routes.py`：新增 `GET /workspace/conversations/{id}/messages?after_id=` 与 `POST /workspace/conversations/{id}/messages`（`Idempotency-Key`）。
  - `packages/contracts/openapi.json`、`apps/chat/lib/api-types.ts`、`apps/workspace/lib/api-types.ts`：重新生成。
  - `apps/workspace/features/conversation/`：回复/轮询请求、`useConversationMessages` hook、实时消息区与回复框组件；`ConversationGate` 接入 3s 轮询并在 `HUMAN_ACTIVE` 显示回复框。
  - `apps/workspace/tests/`：新增/更新组件测试。
  - `tests/integration/`（待创建）：`test_workspace_reply_AC_37.py`。
  - `scripts/trace-baseline.txt`：删除 AC-37 占位（测试落地后）。
- 本次不改变：
  - 状态机：回复不改变会话/交接单状态；关闭与转回留 F-11/F-12。
  - 错误码集合：不新增错误码；继续用 `NOT_FOUND`/`CONVERSATION_CLOSED`。
  - `apps/chat` 代码：客户消息轮询（F-02）与 `agent`/`system` 消息渲染已满足“客户 3s 内看到回复”。
  - 审计与限速（F-13）；本卡不写 `service_audit_events`。
  - 交接单 `pending_step` 语义：回复阶段保持原值，由 F-12 关闭/转回统一（见 §2.3 D-5、§7）。
  - 队列轮询：F-06/F-07 已确定打开/重试时拉取一次；本卡只轮询会话页消息，不改队列。

## 2. 任务级决策

### 2.1 需人类决策

无。AC-37 的语义（回复持久化、客户 3s 轮询可见、人工中客户消息不触发 AI、消息不丢）已由 brief/plan 批准；本卡只补齐 plan 已列 API 的实现与前端接线。

### 2.2 声明的 seam

| ID | 内部接口 | 为什么测试直接驱动它 |
|---|---|---|
| S-1 | `POST /workspace/conversations/{conversation_id}/messages` | 回复持久化、归属/状态门禁、幂等重放与零副作用 |
| S-2 | `GET /workspace/conversations/{conversation_id}/messages?after_id=` | 工作台增量轮询、状态回传、越权 404 |
| S-3 | `GET /customer/messages?after_id=` | 客户侧游标能读到坐席回复，且顺序稳定 |
| S-4 | `POST /customer/messages` | 人工中客户消息只落库、不调用模型、不新建交接单 |

### 2.3 实现者自行决定

| ID | 问题 | 决定 | 理由 | 返工代价 |
|---|---|---|---|---|
| D-1 | 非 `HUMAN_ACTIVE`（已领取未接管）时回复的返回 | 404 `NOT_FOUND`；已关闭仍 409 `CONVERSATION_CLOSED` | plan 状态机只定义 `HUMAN_ACTIVE` 可回复，错误码集合是封闭的；用 404 与既有“归属不可见”一致，不新增错误码 | 小（若需可区分状态，改错误码并重导契约） |
| D-2 | 回复是否需要幂等键 | 需要；请求头 `Idempotency-Key`（1–64），复用 `service_messages` 唯一约束 `(conversation_id, idempotency_key)`，重放返回原消息 | INV-07 要求所有写操作幂等；与 F-02 客户消息同款，前端重试不会产生重复回复 | 小 |
| D-3 | 工作台消息页的响应契约 | 复用 `MessagePageResponse`（`conversation_id`/`status`/`after_id`/`messages`） | 与客户侧轮询同构，前端一套去重/游标逻辑；避免为相同结构新增两个 schema | 小 |
| D-4 | 工作台轮询位置与频率 | 会话页打开后 3s 轮询 `GET .../messages`，`status` 取消息页返回值；不轮询队列与详情 | plan 3.3.3 明确“轮询每 3s，`after_id` 为消息 ID”；状态变化（如后续 F-11 关闭）由消息页回传，详情只在进入/接管时读 | 小 |
| D-5 | 接管后 `pending_step` 仍为“等待坐席接入” | 本卡不改；由 F-12 在关闭/转回时统一定义 | AC-37 不涉及待办；F-08 已走查该读模型，单独改会把 F-11/F-12 的语义提前 | 小（F-12 一并处理） |
| D-6 | 工作台消息列表与交接单快照并存 | 两者都保留：快照是“转人工时”的上下文，消息区是实时流 | 删掉快照会回退 F-08 已评审的上下文展示；两者语义不同，不合并 | 小 |
| D-7 | 回复框显示条件 | 仅 `HUMAN_ACTIVE` 显示；`CLAIMED` 只显示“接管后回复” | 与 D-1 的服务端门禁一致，避免前端给出会被 404 的入口 | 小 |
| D-8 | 回复长度与前端限制 | 500 字，前后端一致；超限 422 且无副作用 | 与客户消息一致（plan 3.3.3 “坐席回复限制长度”） | 小 |
