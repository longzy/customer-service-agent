## 1. 改变范围

- 本卡交付的用户可感知行为（只能一个）：客户在任意未关闭状态（`AI_ACTIVE`/`QUEUED`/`CLAIMED`/`HUMAN_ACTIVE`）点“结束会话”，会话与 open 交接单在同一事务内关闭；页面变为只读；关闭后再发消息收到 409 `CONVERSATION_CLOSED`。
- 涉及层：后端（服务 + API）、契约（OpenAPI 与两个前端类型）、前端（仅 `apps/chat`；`apps/workspace` 只补 `app/error.tsx` 承接项，不改页面）。

- 本次改变：
  - `backend/conversations/customer_close.py`（待创建）：客户关闭会话的条件状态转换、open 交接单终态化、系统消息。
  - `backend/api/customer_routes.py`：新增 `POST /customer/session/close`。
  - `packages/contracts/openapi.json`、`apps/chat/lib/api-types.ts`、`apps/workspace/lib/api-types.ts`：重新生成。
  - `apps/chat/lib/session.ts`：新增 `closeSession()` 请求。

  - `apps/chat/features/chat/components/ChatShell.tsx`：状态条旁“结束会话”按钮；`CLOSED` 隐藏输入区。
  - `apps/chat/app/error.tsx`、`apps/workspace/app/error.tsx`（待创建）：FE-NEXT-03 的 `error.tsx`；workspace 一条由 F-10 评审承接。
  - `apps/chat/tests/ChatShell.test.tsx`：新增 AC-38 前端用例。

## 2. 任务级决策

### 2.1 需人类决策

无。AC-38 的客户关闭语义已由 brief/plan 批准；本卡只补齐 plan 已列 API 与前端接线。

### 2.2 声明的 seam

| ID | 内部接口 | 为什么测试直接驱动它 |
|---|---|---|
| S-1 | `POST /customer/session/close` | 任意未关闭状态可关闭、同事务终态交接单、关闭后 409、重复关闭幂等 |
| S-2 | `GET /customer/messages?after_id=` | 关闭后仍可读历史且返回 `status=CLOSED`（读不是写） |
| S-3 | `GET /workspace/queue` | 客户关闭排队会话后队列不再出现该单 |
| S-4 | `GET /workspace/conversations/{id}/messages` | 坐席轮询能看到 `status=CLOSED` 与关闭系统消息（F-10 D-4 的状态回传） |

### 2.3 实现者自行决定

| ID | 问题 | 决定 | 理由 | 返工代价 |
|---|---|---|---|---|
| D-1 | 关闭是否需要 `Idempotency-Key` | 不需要；用 `UPDATE ... WHERE status <> 'CLOSED'` 条件转换实现幂等，重复关闭返回 200 + `CLOSED` 空页 | 关闭是“目标状态唯一”的状态转换，不是创建业务实体；重放零副作用，系统消息由条件更新成功的那一次唯一写入。与 F-10 回复（创建消息，需要幂等键）语义不同。INV-07 的意图由幂等结果满足 | 小（若评审要求键，补请求头并记录系统消息幂等键） |
| D-2 | 关闭响应契约 | 复用 `MessagePageResponse`（`conversation_id`/`status`/`after_id`/`messages`） | 与客户消息读写同构，前端复用 `applyPage` 的游标与去重；首次关闭返回系统消息，重复关闭返回空列表 | 小 |
| D-3 | 关闭后的前端行为 | 停止 3s 轮询、隐藏输入区、状态条显示“已结束”、隐藏“结束会话”按钮 | 关闭是终态，继续轮询没有新消息；隐藏入口避免给出必然 409 的操作 | 小 |
| D-4 | 系统消息与交接单 `pending_step` | 写一条 system 消息“会话已结束”；open 交接单 `pending_step='会话已结束'`，`version+1` | plan 3.4 要求关闭写系统消息；F-10 D-5 的待办语义在 F-12 统一，本卡先给客户关闭的终态值，F-12 转回沿用同一规则 | 小 |
| D-5 | 并发下锁顺序 | 先更新交接单，再条件更新会话（与领取/接管的 `handoff → conversation` 顺序一致） | 交叉顺序会在“客户关闭 vs 坐席领取”并发时形成行锁死锁；同序后由交接单行锁串行化 | 中（若顺序错误，需并发测试会暴露） |
| D-6 | 关闭端点错误码 | 未登录 401；客户无任何会话 409 `CONVERSATION_CLOSED`；重复关闭 200 | 错误码集合封闭；无会话与已关闭对客户都是“没有可关闭的会话” | 小 |
| D-7 | 已在 `CLOSED` 但请求再次关闭 | 返回 200 + `status=CLOSED` + `messages=[]`，不重写 `closed_at` | 与 D-1 一致；前端重试/双击不会出现错误态 | 小 |
| D-8 | `error.tsx` | 两个 app 各补一个 `"use client"` 错误边界，复用既有 `app`/`content`/`error-box`/`ghost` 样式 | FE-NEXT-03 要求；workspace 一条由 F-10 评审承接。不新增全局样式与颜色字面量 | 小 |
