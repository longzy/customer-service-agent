## 1. 改变范围

- 本卡交付的用户可感知行为（只能一个）：客户转人工后，坐席在队列摘要与会话详情看到该客户名下最近订单摘要与真实订单数；无订单时订单数为 0 且不写空摘要；订单信息不可用时有明确状态；第二坐席仍 404。
- 涉及层：conversations（`handoffs.py` 交接单上下文、`customer_chat.py` 转人工路径取快照、`workspace_conversations.py` 详情/队列读模型、`schemas.py` 契约）、OpenAPI 前端类型、测试、文档；无迁移、无新路由。

- 本次改变：
  - `backend/conversations/handoffs.py`：`create_handoff` 增加 `orders` 与 `order_context_status` 参数；context 写 `order_count=len(orders)`、非空才写 `orders`（AC-55 不写空摘要）、总是写 `order_context_status`（`ok`/`empty`/`failed`）。
  - `backend/conversations/customer_chat.py`：
    - 新增 `_handoff_order_snapshot`：优先复用本会话最近一条非空 `payload.orders`（不实时查 OMS）；无快照时按 plan 3.1 补查一次最近订单；
    - `_queue_for_handoff` 增加 `customer`/`order_gateway`/`orders`/`order_context_status`，透传给 `create_handoff`；
    - 关键词转人工（客户主动要人）：复用快照，无快照时补查一次最近订单（含写 `order_query` AI 事件）；补查失败不阻塞转人工，状态记 `failed`；
    - 订单连续失败转人工：不再查 OMS（已知不可用），`orders` 空、状态 `failed`，复用既有 `failure_count`/`last_error`；
    - 模型失败/模型判定转人工：只复用本会话快照，不补查（避免放大 OMS 调用与 001 事件序列）。
  - `backend/conversations/workspace_conversations.py`：`HandoffDetail` 增加 `orders`（白名单摘要）与 `order_context_status`；`list_queued_handoffs` 的 `order_count` 改为交接单快照值（plan 3.5）。
  - `backend/conversations/schemas.py`：`WorkspaceHandoffDetail` 增加 `orders` 与 `order_context_status`；订单字段只含白名单。
  - `make gen-contracts`：刷新 `openapi.json` 与 `apps/workspace/lib/api-types.ts`（`apps/chat` 类型同步生成物）。
  - 测试：
    - 新增 `tests/integration/test_order_query_AC_55.py`、`tests/integration/test_order_query_AC_56.py`；
    - 修订 001 中与 `order_count` 直接冲突的断言：`test_customer_handoff_AC_32.py` 关键词用例的 `order_count`/事件数/AI 轨迹断言、`test_customer_handoff_triggers_AC_32.py` 的订单列表查询次数、`test_workspace_queue_AC_35.py` 队列订单数用例；
    - 同步 001 brief AC-35/36 文本中 `order_count=0` 为"交接单快照订单数"（003 brief 已登记的同步事项）。
  - 文档：`features.md` F-28 行、`CURRENT.md`、`scripts/trace-baseline.txt`（AC-55/56 退出待开工豁免）、本卡证据。

- 本次不改变：
  - 客户侧订单卡片、工作台订单区渲染与 ui-spec（F-29）；审计 `order.queried`、Tool Trace 指标、评测（F-29）；001 AC-31/32 中除 `order_count` 外的其余文本同步（F-29）；
  - 会话状态机、关键词/模型失败分级判定与文案、订单查询回复模板；
  - 交接单的 `verified_order_ids`/取消工作流；不新增 HTTP 路由；迁移与 `packages/contracts/tools/*.json` 不改。

## 2. 任务级决策

### 2.1 需人类决策

无。AC-55/56、`order_count` 口径（最近 ≤5 条）与"不写空摘要"已由 brief/plan 批准。

### 2.2 声明的 seam

| ID | 内部接口 | 为什么测试直接驱动它 |
|---|---|---|
| S-1 | `POST /customer/messages`（关键词/模型/失败转人工路径） | 走完整消息路径：转人工时交接单上下文、会话状态、系统提示 |
| S-2 | `service_handoffs.context`（`orders`/`order_count`/`order_context_status`） | 交接单是坐席可见订单上下文的唯一事实源 |
| S-3 | `GET /workspace/conversations/{id}` 与 `GET /workspace/queue` | 工作台读模型必须与交接单快照一致；第二坐席仍 404 |
| S-4 | `service_messages.payload`（成功查询快照） | 复用口径的证据：转人工前查过的单不被重新查询覆盖 |

### 2.3 实现者自行决定

| ID | 问题 | 决定 | 理由 | 返工代价 |
|---|---|---|---|---|
| D-1 | 快照复用口径 | 本会话最近一条 `author_type=ai` 且 `payload.orders` 非空的快照（按消息 id 倒序，最多回看 20 条）；找到即复用，不再查 OMS | plan 3.1 关键决策 5"已有成功查询快照则复用"；避免坐席打开/转人工放大 OMS 调用 | 小 |
| D-2 | 无快照时补查范围 | 仅关键词转人工（客户主动要人）补查一次 `list_recent_orders`（plan 3.1 明示）；模型失败/模型判定转人工只复用快照，不补查 | 模型失败≠OMS 失败，但补查会放大 OMS 调用并扰动 F-24/001 既有事件序列；plan 只对"客户直接说转人工"要求补查 | 小 |
| D-3 | 订单连续失败转人工 | 不再调用 OMS，`orders` 空、状态 `failed` | 已知 OMS 不可用，再查只会增加延迟与失败；AC-53 的事件序列不被额外查询污染 | 小 |
| D-4 | 订单上下文状态 | `order_context_status`：`ok`（有订单）、`empty`（查无/未绑定/无订单）、`failed`（补查 OMS 失败）、`unknown`（AI 主动转人工且无已查快照，未发起查询）；旧交接单缺字段时按 `orders` 非空推断，否则 `unknown` | AC-56 要求 OMS 异常有明确提示；仅靠 `orders` 空列表无法区分"无订单"、"不可用"与"未查询"（Spec 复核建议） | 小 |
| D-5 | 队列 `order_count` | 读交接单 `context.order_count`，不再恒 0 | plan 3.5"队列详情抽屉的订单指标改为真实 order_count"；数据只读快照 | 小 |
| D-6 | DTO 订单字段 | 白名单 `order_id`/`item_summary`/`order_status`/`status_label`/`amount_cents`/`currency`/`created_at`/`created_at_local`；最多 5 条；不返回 `items`/手机号/支付信息 | plan 3.2 白名单；AC-56 只显示该客户名下订单 | 小 |
| D-7 | 补查是否写 AI 事件 | 写 `event_type=order_query`、`name=list_recent_orders`（成功/查无/失败） | 查询事实必须留痕，F-29 的指标/审计在此基础上接 | 小 |
| D-8 | "不写空摘要" | `orders` 键仅在非空时写入 context；`order_count` 与 `order_context_status` 总是写 | AC-55 原文；状态字段不是摘要 | 小 |
| D-9 | 工作台是否实时查 OMS | 不查，只读交接单快照 | plan 3.3；OMS 异常只在客户查询时暴露，详情/关闭/转回不被阻塞（AC-56） | 小 |
| D-10 | 详情 orders 缺字段兜底 | 非 dict 元素丢弃；`order_count` 与 `len(orders)` 不一致时以 `order_count` 为准展示计数，`orders` 只展示可解析项 | 旧数据/手工种子可能只有计数没有明细；读模型不猜业务含义（沿用既有 `_int_value`/`_dict_list` 风格） | 小 |
| D-11 | 评审整改：订单状态类型 | `OrderContextStatus = Literal["ok","empty","failed"]` 贯穿 `handoffs`/`customer_chat`/`workspace_conversations`；`schemas` 保持独立的同值字面量（契约层不反向依赖业务模块）；旧单缺字段或未知值按 orders 推断，不击穿 DTO 校验 | 去掉 `# type: ignore[arg-type]`，未知状态不产生 500（Standards 建议 3） | 小 |
| D-12 | 评审整改：口径回写 | 003 brief AC-55 与成功度量改为"交接单快照条数"；plan 3.3/未决问题 1 同步；001 AC-35/36 文本同步 | 避免"本人最近订单条数"与"复用单笔快照"两种读法（Spec 条件①） | 小 |
