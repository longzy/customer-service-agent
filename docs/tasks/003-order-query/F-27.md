# 任务执行卡：F-27 订单查询失败分级

- 关联 feature：F-27
- 依据：`docs/specs/003-order-query/requirements.md` AC-53；`docs/specs/003-order-query/design.md` 3.4、3.6；[ADR-0011](../../adr/0011-model-failure-degradation.md)
- 绑定验收：AC-53（单次失败提示重试、连续两次转人工、订单失败不并入模型失败计数）
- 变更级别：T3（订单归属、转人工状态机入口、失败降级）
- 设计引用：失败文案、reason/trigger 与交接单字段以 plan 3.4 为准；本卡只定实现 seam 与连续判定规则

## 1. 改变范围

- 本卡交付的用户可感知行为（只能一个）：OMS 超时/异常/非法响应时客户看到"可重试"提示且不建单；同一会话连续两次订单查询失败自动转人工并说明原因；订单失败与模型失败互不计数。
- 涉及层：conversations（`order_queries.py` 失败结果、`customer_chat.py` 失败落地与转人工）、workspace（交接单原因标签与筛选）、测试、文档；无迁移、无契约变更。

- 本次改变：
  - `backend/conversations/order_queries.py`：失败状态集合（`timeout`/`error`）与转人工文案常量（供消息层与测试共用）。
  - `backend/conversations/customer_chat.py`：
    - `_recent_ai_events` 抽取模型/订单共用的"最近 N 条指定类型事件"查询；
    - `_consecutive_order_failures`：同会话最近两条 `order_query` 事件均失败才计为连续；成功/查无事件与"已转回 AI 客服"系统消息打断计数；
    - `_order_result`：单次失败只写 AI 提示；连续 2 次失败改走 `_queue_for_handoff`（`reason=ORDER_QUERY_FAILURE`、`trigger=order_query_failure`、`failure_count`、`last_error`），写系统提示「订单查询连续失败，已为你转接人工。」；
    - 单笔、候选、确定性列表、模型订单意图四条路径共用 `_order_result`，失败分级自动覆盖。
  - `apps/workspace`：队列表格/详情与会话详情的 `REASON_LABEL` 增加 `ORDER_QUERY_FAILURE → 订单查询失败`，队列原因筛选增加该项；会话详情失败次数标签按 reason 区分「连续订单失败」/「连续模型失败」。
  - 测试：新增 `tests/integration/test_order_query_AC_53.py`（超时/异常/非法响应单次、连续两次、成功清零、双向计数隔离、转回重置、候选列表失败）；`tests/integration/customer_support.py` 抽取 `simulate_return_to_ai` 供 AC_31/AC_53 共用；`apps/workspace/tests/ConversationGate.test.tsx` 增加 AC-53 原因标签用例。
  - 文档：`tasks.md` F-27 行、`STATUS.md`、`scripts/trace-baseline.txt`（AC-53 退出待开工豁免）、本卡证据。

- 本次不改变：
  - 会话状态机本身、关键词转人工、模型失败分级（F-24）的判定与文案；
  - 交接单订单摘要与 `order_count`（F-28）、工作台订单区（F-28）、审计 `order.queried` 与评测（F-29）；
  - 不新增 HTTP 路由；`packages/contracts/tools/*.json`、迁移不改。

## 2. 任务级决策

### 2.1 需人类决策

无。失败分级、文案、reason/trigger 与字段已由 brief AC-53 / plan 3.4 / ADR-0011 批准。

### 2.2 声明的 seam

| ID | 内部接口 | 为什么测试直接驱动它 |
|---|---|---|
| S-1 | `POST /customer/messages`（订单失败路径） | 走完整消息路径：会话状态、AI 消息/系统提示、交接单 |
| S-2 | `service_ai_events`（`event_type=order_query`、`status=timeout|error`） | 连续判定与计数隔离的唯一事实源 |
| S-3 | `service_handoffs`（`reason`、`context.trigger/failure_count/last_error`） | 证明转人工原因、次数与最后错误可被坐席看到 |

### 2.3 实现者自行决定

| ID | 问题 | 决定 | 理由 | 返工代价 |
|---|---|---|---|---|
| D-1 | "连续两次订单失败"的判定口径 | 取同会话最近两条 `order_query` 事件；均为 `timeout`/`error` 才算连续 | plan 3.4 的"连续两次查询失败"指查询序列；普通聊天不写订单事件，不算打断 | 小 |
| D-2 | 什么打断计数 | 最近的 `ok`/`not_found` 订单事件；以及"已转回 AI 客服"系统消息之后重新计数 | 成功查询必须清零（plan 3.4）；转回是新的起点，与 F-24 一致 | 小 |
| D-3 | 单次失败是否写交接单 | 否；只写 AI 提示并保持 `AI_ACTIVE` | AC-53；ADR-0011 单次失败不建单 | 小 |
| D-4 | 第二次失败是否再写"可重试"AI 消息 | 否；只写转人工系统提示 | plan 3.4 连续失败文案；避免同一条客户消息收到两条相反指引 | 小 |
| D-5 | 交接单 reason/trigger | `reason=ORDER_QUERY_FAILURE`、`trigger=order_query_failure` | plan 3.4 指定 trigger；ADR-0011 的 `TOOL_FAILED` 是失败类别而非 reason 码，沿用 `MODEL_UNAVAILABLE` 式的具体码便于工作台展示与筛选（≤32 字符） | 小 |
| D-6 | `last_error` 取值 | `outcome.error_code`；为空时兜底 `ORDER_QUERY_FAILED` | 保留 gateway 归一后的错误码；超时因 `get_order` 契约未声明 `DEPENDENCY_TIMEOUT`，记 `DEPENDENCY_UNAVAILABLE` | 小 |
| D-7 | 计数隔离方式 | 订单失败只写 `event_type=order_query`，模型失败只读 `event_type=model` | 两套计数按事件类型天然隔离，不引入额外列 | 小 |
| D-8 | 失败文案常量位置 | `order_queries.py` 放失败状态集合与转人工文案；`customer_chat.py` 放 reason/trigger | 与既有 `UNAVAILABLE_REPLY`、`MODEL_FAILURE_HANDOFF_NOTICE` 的分层一致 | 小 |
| D-9 | 评审整改：工作台原因可读性 | 队列表格/详情/会话详情 `REASON_LABEL` 与原因筛选增加 `ORDER_QUERY_FAILURE → 订单查询失败`；失败次数标签按 reason 区分「连续订单失败」/「连续模型失败」 | 坐席不应看到原始码；F-24 的 `MODEL_UNAVAILABLE` 已有先例 | 小 |
| D-10 | 评审整改：重复代码 | 抽 `_recent_ai_events` 供两套连续失败查询共用；`simulate_return_to_ai` 下沉 `tests/integration/customer_support.py` 供 AC_31/AC_53 共用 | 两条查询只差事件类型与"连续"边界；转回现场两个 AC 逐字重复 | 小 |
