# 任务执行卡：F-29 订单卡片、可观测与评测收口

- 关联 feature：F-29
- 依据：`docs/specs/003-order-query/requirements.md` AC-55、AC-56、AC-57、AC-58；`docs/specs/003-order-query/design.md` 3.5、3.6、3.7、5.1、5.2；[ui-spec](../../design-system/ui-spec.md) 3.5、3.10、4
- 绑定验收：AC-57（每次订单查询有审计、工具记录与 Trace 关联，审计失败 503）、AC-58（客户聊天订单卡片，含字段、三态、可访问性与 375/900/1200/1440 无溢出）；回归 AC-55/AC-56 的前端渲染部分与 001 AC-31/32
- 变更级别：T3（订单隐私、审计、客户可见事实）
- 设计引用：查询判定、回复模板、交接单快照口径以 plan 3.1–3.4 与 F-25~F-28 为准；本卡只定前端呈现、可观测 seam 与契约收紧

## 1. 改变范围

- 本卡交付的用户可感知行为（只能一个）：客户在聊天里看到结构化订单卡片，坐席在会话详情看到同一份订单快照与空/不可用/未查询状态；每次查询可在审计与 Trace 里查到，评测覆盖订单场景。
- 涉及层：conversations（`order_queries`、`customer_chat`、`customer_http`、`schemas`）、audit（事件常量与 metadata 白名单）、platform/metrics（标签计数）、OpenAPI 前端类型、apps/chat、apps/workspace、evals、ui-spec；无迁移、无新路由、无状态机改动。

- 本次改变：
  - `backend/platform/metrics.py`：新增带标签的计数器（`increment_labeled`）与 `render()` 分组输出；保留 `increment`/`snapshot` 的无标签语义与现有调用方。
  - `backend/platform/observability.py`：把 `get_order`/`list_recent_orders` 加入 `ALWAYS_SAMPLE_TOOLS`，保证成功查询也写 `tool_executions`（AC-57；默认 5% 尾采样会丢成功记录）。
  - `backend/conversations/order_queries.py`：`query_order` / `query_recent_orders` 在返回前记录 `order_query_total{tool,status}`、`order_query_latency_ms_total`、未绑定时 `order_query_unbound_total{tool}` 与一条结构化日志；`OrderQueryOutcome` 增加 `order_id` 与 `unbound`，供审计区分单笔/列表与未绑定。
  - `backend/conversations/customer_chat.py`：`ChatResult` 增加 `order_query: OrderQueryAudit | None`；`_order_result`、`_handoff_order_context`、`_queue_for_handoff`、`_queued_result` 透传本次查询的审计信息；幂等重放不带审计。
  - `backend/conversations/customer_http.py`：消息处理成功后，若结果带订单查询且非重放，调 `audit_or_503` 写 `order.queried`（entity=order、entity_id=订单号或会话 id、metadata 含 `conversation_id`/`order_id`/`order_count`/`result`/`tool`/`error_code`）。
  - `backend/audit/service.py`：新增 `ORDER_QUERIED = "order.queried"` 与导出；`AUDIT_METADATA_KEYS` 增加 `order_id`、`order_count`、`result`、`tool`。
  - `backend/conversations/schemas.py`：新增 `OrderSummaryPublic`（白名单字段）与 `MessagePayload`；`MessagePublic.payload: MessagePayload | None`；交接单订单明细复用同一摘要结构。
  - `apps/chat`：新增 `features/chat/lib/orderStatus.ts`、`lib/format.ts` 的金额格式化、`features/chat/components/OrderCard.tsx`；`MessageList` 在 AI 消息 `payload.orders` 非空时渲染卡片列表（≤5 张，页脚“查询时状态”）。
  - `apps/workspace`：新增 `features/conversation/components/OrderSummaryList.tsx`；`ConversationDetailPanel` 增加“最近订单”区，渲染 `ok`/`empty`/`failed`/`unknown` 四态。
  - 测试：新增 `tests/integration/test_order_query_AC_57.py`、`tests/integration/test_order_query_AC_58.py`、`tests/integration/test_eval_scenarios.py`、`apps/chat/tests/OrderCard.test.tsx`、`apps/workspace/tests/ConversationOrders.test.tsx`；单测补 metrics 标签与订单 outcome 审计字段。

  - `make gen-contracts`：刷新 `openapi.json`、`apps/chat`/`apps/workspace` 的 `lib/api-types.ts`（payload 结构化）。

### 2.2 声明的 seam

| ID | 内部接口 | 为什么测试直接驱动它 |
|---|---|---|
| S-1 | `POST /customer/messages` 响应 `payload.orders` | 客户卡片唯一数据源；AC-58 的字段与白名单断言 |
| S-2 | `service_audit_events` 的 `order.queried` | AC-57 要求可查客户、会话、订单号、结果；审计失败必须 503 |
| S-3 | `tool_executions`（`tool_name`/`trace_id`/`latency_ms`/`error_code`） | AC-57 要求工具记录且不含 PII；Trace 可按 trace_id 关联 |
| S-4 | `GET /workspace/conversations/{id}` 的 `handoff.orders`/`order_context_status` | AC-55/56 的前端渲染；空/不可用/未查询状态文案直接来自该 seam |
| S-5 | `order_query_total` / `order_query_latency_ms_total` / `order_query_unbound_total` | plan 3.6 要求指标；未绑定与查无不混淆 |

### 2.3 实现者自行决定

| ID | 问题 | 决定 | 理由 | 返工代价 |
|---|---|---|---|---|
| D-1 | 审计写在哪一层 | HTTP 层：`ChatResult.order_query` 带回查询事实，`customer_http` 用现有 `audit_or_503` 写 | 审计 writer 只在 API 层注入；沿用“同事务、失败 503 回滚”语义，业务模块不依赖审计基础设施 | 小 |
| D-2 | 哪些查询要审计 | 消息触发的单笔/最近查询，以及关键词转人工时的补查；模型主动转人工不补查则无审计 | AC-57 是“每次订单查询”；补查也是真实查询，必须留痕 | 小 |
| D-3 | 幂等重放是否重复审计 | 不重复：`_replay` 返回的 `ChatResult` 不带 `order_query` | 重放没有真实查询，重复审计会污染计数 | 小 |
| D-4 | 指标命名与延迟口径 | `order_query_total{tool,status}` 为标签 counter；延迟累加 `order_query_latency_ms_total`（毫秒整数）；未绑定另记 `order_query_unbound_total{tool}` | plan 的 `order_query_latency_ms` 是数值指标，现有 metrics 只有 counter；用 `_total` 明确累加语义，不引入直方图基础设施 | 小 |
| D-5 | metrics 扩展方式 | 新增独立 `_labeled` 存储与 `increment_labeled`；`snapshot()` 把标签键拍平为 `name{k="v"}`，`render()` 按指标名分组输出 TYPE 行 | 不破坏既有无标签调用与测试；避免在指标名里手拼非法 TYPE 行 | 小 |
| D-6 | payload 契约 | 新增 `MessagePayload.orders: list[OrderSummaryPublic]`；交接单订单明细复用 `OrderSummaryPublic` | 前端类型只能来自 OpenAPI（FE-DATA-01）；否则前端要手写订单字段 | 中（需刷新契约与前端类型） |
| D-7 | 订单卡片组件位置 | 放 `features/chat/components/OrderCard.tsx`、workspace 放 `features/conversation/components/OrderSummaryList.tsx`，不按 plan 3.5 的 `components/ui/` | 卡片有固定中文文案与业务字段，按 FE-CMP-01 属业务组件；plan 的路径是建议而非验收项 | 小 |
| D-8 | 客户侧三态 | 加载态由消息骨架承担；无 `payload.orders`（查无/失败）不渲染卡片，由 AI 文案给出下一步；不新增独立加载组件 | plan 3.5 明示“加载态不单独做”，避免同一段订单数据出现两套加载语义 | 小 |
| D-9 | 工作台四态文案 | `ok` 列订单；`empty`→“该客户名下暂无订单”；`failed`→“订单信息暂不可用”；`unknown`→“该会话未查询订单”；最多 5 条 | `empty` 与 `unknown` 不能混为“暂无”，否则坐席会误判客户名下无单（F-28 D-4） | 小 |
| D-10 | 评测场景载体 | 新增 `tests/integration/test_eval_scenarios.py`，测试名带 `_AC_XX`，由 `evals/run.py` 的 `SCENARIO_MODULE` 统计 | 复用现有 AC 聚合与场景统计，不新增评测框架 | 小 |
| D-11 | 001 AC-31/32 同步 | 不新增改动；F-26/F-28 已同步文本与断言，本卡只跑回归并在证据中确认 | 避免重复修订同一契约 | 小 |
| D-12 | 订单工具是否强制采样 | `get_order`/`list_recent_orders` 加入 `ALWAYS_SAMPLE_TOOLS`，成功查询 100% 写 `tool_executions` | AC-57 要求每次查询有工具记录；隐私敏感读被 5% 尾采样丢掉会让“查了谁的单”不可追溯 | 小 |
| D-13 | 旧消息载荷读模型 | `MessagePayload.from_stored` 只投影 `orders`、过滤非对象与校验失败项；历史非订单载荷不再透传 | 保持白名单与旧数据兼容，坏行不击穿页面；写入侧仍由构造函数校验（Standards 建议 1） | 小 |
| D-14 | AC-57“每次查询”的边界 | 指实际调用 OMS：未绑定客户按 plan 3.2 不调用 OMS，因此只写 `order.queried` 与 `order_query_unbound_total`，无 `tool_executions`；测试显式断言该豁免 | 未绑定没有数据面，凭空造工具记录会伪造下游调用（Spec 条件 1） | 小 |
| D-15 | 查无的工具记录语义 | 他人/不存在订单在 `ToolGateway` 归属闸门被 `rejected`（不调用 OMS），工具记录 `result_status=rejected`、错误码 `NOT_FOUND_OR_UNAUTHORIZED`；审计仍为 `not_found` | 与安全闸门语义一致；审计与工具记录各自表达“客户看到什么”和“系统为何拒绝”（Spec 条件 1） | 小 |
| D-16 | 列表查询审计实体 | 单笔 `entity_type=order`、`entity_id=订单号`；列表 `entity_type=conversation`、`entity_id=会话 id` | 不把会话 id 挂在 order 实体上（Standards 建议 3） | 小 |
| D-17 | 审计失败测试精度 | 只让 `order.queried` 失败，验证该审计自身的 503 回滚；断言 `message.sent` 与 `order.queried` 均未落库 | 全失败 writer 只能证明第一条审计失败，覆盖不到订单审计（Spec 证据） | 小 |
