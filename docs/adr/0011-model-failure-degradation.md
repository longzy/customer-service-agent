# ADR-0011：模型失败的分级降级

- 状态：已批准
- 日期：2026-11-19
- 批准：2026-11-19（用户认可方向，先改文档）
- 关联：[001 plan](../specs/001-customer-handoff/design.md)、[001 brief](../specs/001-customer-handoff/requirements.md)、[ADR-0005](0005-enterprise-boundary.md)

## 背景

001 原规格把模型失败统一处理为 `MODEL_UNAVAILABLE`：10s 超时/异常直接创建交接单、会话转 `QUEUED`，客户看到「排队中，请稍候」。

行业调研显示这不是主流做法：

- NICE 的联络中心实践把「低置信」升级人工，但强调升级要保留上下文，并对失败场景做监控与演练；
- Intercom Fin 在客户不满意或明确要求人工时 handoff，而不是模型一报错就 handoff；
- Userflow 的 escalation 触发分三类：用户信号、Agent 限制、风险与合规；其中「低置信」需要检索无结果等佐证信号，「工具调用失败/超时」才作为动作失败触发交接；
- 中文技术实践把失败拆成超时、拒答、低置信：**超时走重试或降级路由，低置信才转人工**，并强调任务级超时预算、有界重试与熔断；
- 常见降级链是「主模型 → 备用模型 → 规则/缓存 → 人工」，人工是最后兜底。

原实现的问题：把基础设施的瞬时故障直接兑换成人工队列；客户没有表达转人工意愿，却看到「排队中」；坐席接到本可自动完成的会话；交接单没有失败次数/错误码，坐席难以判断。

## 决策

### 1. 失败分类

| 类型 | 触发 | 处理 |
|---|---|---|
| `CUSTOMER_REQUEST` | 关键词或 `intent=transfer` | 建交接单（不变） |
| `LOW_CONFIDENCE` | `confidence < 0.6` | 建交接单（不变） |
| `OUT_OF_SCOPE` | 订单/超范围 | 建交接单（不变） |
| `MODEL_TIMEOUT` | 模型 10s 超时 | 单次：提示重试，不建单；同一会话连续 2 次：建单 |
| `MODEL_ERROR` | 模型异常/5xx | 同 `MODEL_TIMEOUT` |
| `TOOL_FAILED` | 工具报错/超时（003/004 后） | 只读查询：提示重试；有副作用的动作：建单并带动作/错误 |

### 2. 单次失败

- 不创建交接单，不改会话状态；
- 返回系统消息：「AI 暂时不可用，你可以重试，或说“转人工”。」；
- 写 `service_ai_events`，保留 `trace_id` 与失败状态；
- 客户重发消息或明确说「转人工」后，按对应路径处理。

### 3. 连续失败

- 同一会话连续 2 次 `MODEL_TIMEOUT`/`MODEL_ERROR`：自动建单，reason=`MODEL_UNAVAILABLE`；
- 系统消息：「AI 暂时不可用，已为你转接人工（排队中）。」；
- 交接单记录失败次数与最后一次错误码，AI 轨迹保留两次失败事件。

### 4. 不做的事

- 不在服务端做阻塞式无限重试；
- 不做多模型自动切换（后续切片评估）；
- 不把「低置信」降级为提示重试：低置信是模型能力边界，人工更合适。

## 后果

- AC-31/AC-32 修订；新增 feature F-24 承接实现，F-02/F-04 的历史证据保留。
- `customer_chat._model_failed` 需要拆成「单次提示」与「连续失败建单」两条路径；需要新增失败计数查询与测试。
- 前端客户聊天需要展示新的系统提示文案；不新增按钮，仍可用自然语言转人工。
- 队列污染减少，但连续失败仍有兜底，保留「无死路」目标。
- 当前实现仍是旧行为；在 F-24 完成前，文档与实现存在已知差异，`STATUS.md` 已登记。

## 拒绝的方案

- **保持「模型失败一律自动转人工」**：瞬时故障占队列，客户不知情，坐席处理无效会话。
- **只提示重试、不自动转人工**：连续失败会把客户卡死，违背「死路 handoff 数为 0」。
- **服务端阻塞重试 3 次**：把后台抖动放大成前台长时间等待；超时预算不可控。
