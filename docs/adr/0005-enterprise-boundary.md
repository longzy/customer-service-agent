# ADR-0005：企业客服边界

- 状态：已批准
- 日期：2026-11-16
- 批准：2026-11-16（R0-1 基线，用户确认）
- 关联：[产品宪章](../product/charter.md)、[路线图](../roadmap.md)、[企业化方向重置](../initiatives/2026-11-16-enterprise-reset.md)
- 取代：M1-P 原型的产品与 Mock 边界；ADR-0002 的订单识别方式由本 ADR 调整，ADR-0001/0003/0004 继续有效
- 后续修订：[ADR-0006](0006-customer-login.md) 已取代本 ADR 的“客户匿名”与“订单号 + 手机尾号校验”决策

## 背景

M1-P 按消费者聊天实现，21/21 原型验收通过，但产品定义与 Mock 边界错误：

- 页面是消费者聊天，却用员工测试账号登录；
- 转人工只锁输入框，没有队列、坐席、接管和回复；
- 身份、session、坐席与模型 fallback 都是演示级；
- 验收按 AC 与接口通过，没有按岗位端到端走通。

继续在 `services/api` 上叠加 M2 只会放大错位。需要一份 ADR 固化企业边界，作为 R0-2 与新 M1 的共同前提。

## 决策

### 1. 产品边界

产品是**企业内部 AI 客服系统**，由两个独立前端组成：

- **客户 Web Chat**：匿名会话，可选昵称；AI 默认自动回复；客户可要求转人工。
- **坐席工作台**：员工登录；队列、领取、接管、回复、关闭、转回 AI。

不把两个岗位塞进同一个页面，也不把消费者 demo 当作企业 MVP。

### 2. 角色与身份边界

- M1 员工角色只有 `agent`；`supervisor`/`admin` 到 M4（2026-11-16 确认）。
- 员工使用本地账号 + 服务端 session；RBAC 在服务端校验，前端隐藏不算授权。
- 客户在 M1 保持匿名，不建客户账号（2026-11-16 确认）。
- 匿名客户访问订单必须通过**订单号 + 下单手机号后四位**校验；服务端向 OMS 验证，校验失败不区分“订单不存在”与“手机号不匹配”，并限速。
- 订单访问授权只在当前会话内复用，新会话重新校验。
- OIDC/SSO/MFA/SCIM 后置到 M5。

### 3. Mock 边界

只有外部业务系统允许 Mock：

| 允许 Mock | 不允许 Mock |
|---|---|
| OMS 订单查询/取消/退款接口 | 员工身份、密码、session、RBAC |
| 支付/物流（M2 及以后） | 客户会话、消息、交接单、队列、分配、接管、回复、关闭 |
| 测试中的模型与外部服务 | 坐席工作台、审计、Trace、持久化 |

约束：

- Mock 只允许存在于 `services/adapters/` 与测试。
- 业务模块只依赖 `OmsPort`，不得 import 具体 Adapter 或 `mock_oms`。
- 生产缺少 OMS 配置时启动失败，不得静默回落 Mock。

### 4. 模块与依赖边界

目标是模块化单体，不引入微服务/Kafka/K8s。R0-2 先立骨架与检查器：

```text
apps/chat/                  # 客户匿名 Web Chat
apps/workspace/             # 坐席工作台
services/api/               # HTTP 入口、鉴权中间件、DTO
services/platform/          # 配置、数据库、outbox、worker、trace
services/identity/          # 员工账号、密码、session、RBAC
services/conversations/     # 会话、消息、交接单、队列、领取/接管
services/agent_runtime/     # 意图、上下文、模型调用、Tool 规划
services/tools/             # Tool Registry 与授权网关
services/workflows/         # 取消等显式流程
services/adapters/oms/      # OmsPort + Mock/Http Adapter + factory
packages/contracts/         # 跨模块契约的唯一定义来源
```

依赖规则：

- `apps/*` 只通过 HTTP 与契约访问后端。
- `agent_runtime`/`tools`/`workflows` 不得 import `services.api`。
- `tools`/`workflows` 不得 import `mock_oms` 或具体 OMS Adapter。
- 只有 `adapters/oms/factory` 读取 OMS 配置并选择 Adapter。
- `packages/contracts` 是跨模块接口的唯一定义来源。

### 5. 验收边界

- M1 出口以客户与坐席两条岗位路径端到端走查为准，不以 AC 数量为准。
- 必须有队列、领取、接管、回复、关闭的真实实现；转人工不得是死路。
- 越权、重复取消、规则不符误提交必须为 0。
- 场景评测覆盖核心路径，并保留可复现证据。

### 6. 对架构不变量的影响

本 ADR 同时修订 `docs/architecture/invariants.md`：

- **INV-01**：调用主体标识从“用户”放宽为“匿名会话或员工用户”。
- **INV-02**：区分员工认证上下文与匿名客户会话，两者都不得被模型或请求正文覆盖。
- **INV-03**：订单授权改为客户订单号 + 手机尾号校验，或坐席接管/队列授权。
- **INV-11**：转人工从“必须可转”加强为“必须有队列、领取与关闭闭环，不得是死路”。
- **新增 INV-17**：工作台接口必须服务端校验角色与会话归属。
- **新增 INV-18**：领取与接管必须防重复和并发冲突。
- **新增 INV-19**：只有外部业务系统允许 Mock，生产缺 OMS 配置启动失败。

## 后果

- R0-2 获得明确的目录、依赖与 Mock 规则，可直接写 `check-imports.py`。
- 新 M1 的范围被限定为“客户 + AI + 坐席”闭环；主管/管理员、客户账号和真实集成延后。
- 匿名客户查单依赖订单号 + 手机尾号，需要 OMS 提供对应校验能力，并把校验记录纳入审计与脱敏。
- 现有 `apps/web` 与 `services/mock_oms` 是 M1-P 资产，需要在 R0-2/M1 中迁移或退役，不能作为新边界继续扩展。
- `ADR-0002` 的业务场景（未发货订单取消）继续有效；其中“本人订单”的识别方式由本 ADR 改为订单号 + 手机尾号校验。

## 拒绝的方案

- 客户也登录后再查单：M1 范围过大，且与“客户匿名”的产品定位冲突。
- 客户侧不做订单操作、只转人工：AI 自动回复没有业务执行能力，退回问答机器人。
- 继续用消费者聊天页 + 测试账号冒充坐席：无法形成队列、接管和审计，企业不可用。
- 把所有身份、会话、队列都先 Mock：主路径不可验证，违背“只有外部系统可 Mock”。
- 直接拆微服务：M1 规模不成立，只会增加分布式事务与调试成本。

## 复审条件

- 客户账号或客户身份体系进入排期；
- OIDC/SSO 或真实 OMS 接入改变身份/订单访问方式；
- M4 引入 `supervisor`/`admin` 后权限模型需要调整；
- 订单号 + 手机尾号方案被业务或合规否决。
